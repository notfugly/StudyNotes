## Функции высшего порядка и замыкания

**Функция высшего порядка** принимает функцию или возвращает её. Функциональный тип явно задаёт параметры и результат.

```kotlin
fun combine(
    a: Int,
    b: Int,
    first: (Int, Int) -> Int,
    second: (Int) -> Int
): Int = second(first(a, b))

val result = combine(1, 2, { x, y -> x + y }, { it * 2 })
// result == 6
```

Если последним аргументом является функция, лямбду можно вынести за круглые скобки:

```kotlin
fun repeatAction(n: Int, action: () -> Unit) {
    for (i in 0 until n) action()
}
repeatAction(3) { println("Hello") }
```

Замыкание удерживает переменную внешней функции:

```kotlin
fun counter(startNum: Int): () -> Unit {
    var i = startNum
    return { println(i++) }
}
val next = counter(123)
next() // 123
next() // 124
```

## Конструкторы, init и проверка состояния

Первичный конструктор задаётся рядом с именем класса. Вторичный использует `constructor` и делегирует инициализацию первичному прямо или через другой вторичный конструктор.

Блок `init` выполняется при создании объекта. В нём проверяют обязательные условия, например `require(points in 0..120)`.

```kotlin
class Student(val name: String, points: Int, initialAge: Int = 0) {
    var points = points
        private set

    var age = initialAge
        set(value) {
            require(value in 0..100) { "Некорректный возраст" }
            field = value
        }

    val isAdult: Boolean
        get() = age >= 18

    init {
        require(points in 0..120)
        require(initialAge in 0..100)
    }

    constructor(name: String) : this(name, 0, 0)
}
```

**Важная особенность:** присвоение начального значения через инициализатор свойства не вызывает пользовательский сеттер. Поэтому проверка возраста только в `set` не проверит `initialAge`; нужна отдельная проверка в `init`.

`field` — обращение к полю хранения свойства. Присваивание `age=value` из самого сеттера вызвало бы рекурсию. Вычисляемое `isAdult` не хранит отдельную копию признака, поэтому автоматически отражает текущий возраст.

## Области видимости и защита коллекции

| Модификатор | Область доступа |
|---|---|
| `public` | доступен извне |
| `private` | внутри соответствующего класса или файла |
| `protected` | внутри класса и его наследников |
| `internal` | внутри модуля |

```kotlin
open class Chat {
    protected val storedMessages = mutableListOf<String>()
    val messages: List<String>
        get() = storedMessages.toList()

    fun addMessage(message: String) {
        storedMessages.add(message)
    }
}

class ModernChat : Chat() {
    fun getLastMessageId(): Int = storedMessages.lastIndex
}
```

Если публичный геттер возвращает исходный `MutableList`, внешний код получает возможность менять содержимое. `toList()` в этом примере отдаёт отдельный снимок списка. Один только `val` не защищает элементы изменяемой коллекции.

## lateinit и lazy

**`lateinit var`** позволяет отложить присвоение ненулевому свойству подходящего ссылочного типа. Чтение до присвоения вызывает `UninitializedPropertyAccessException`. Это не nullable-значение и не автоматическая загрузка.

**`by lazy`** откладывает вычисление до первого чтения и затем сохраняет результат:

```kotlin
class DescriptionHolder {
    lateinit var ipAddress: String

    val description: String by lazy {
        println("Загрузка описания")
        "Описание"
    }
}
```

При двух последовательных чтениях `description` тело инициализации выполняется один раз. В отличие от `lateinit`, здесь описан способ получения значения.

## Наследование и полиморфизм

```kotlin
open class Person(var name: String) {
    open fun introduce(): String = "Привет! Меня зовут $name"
}

class Teacher(name: String, val subject: String) : Person(name) {
    override fun introduce(): String = "$name преподаёт $subject"
}

class Administrator(name: String) : Person(name) {
    override fun introduce(): String = "$name — администратор"
}

val teacher: Person = Teacher("Иван", "Kotlin")
println(teacher.introduce())
```

**Полиморфизм:** переменная имеет тип базового класса `Person`, но переопределённый метод выбирается по фактическому объекту `Teacher`. `open` открывает возможность наследования и переопределения, `override` реализует новое поведение.

### super и вызов готового поведения

В дополнении к `Lesson 3.kt` от 20 октября у `Animal.sound()` появилось тело, а новый наследник `Rat` вызывает его через `super.sound()`. Сокращённый пример:

```kotlin
open class Animal(val name: String) {
    open fun sound() {
        println("Животное $name звуки")
    }
}

class Rat(name: String) : Animal(name) {
    override fun sound() {
        super.sound()
    }
}
```

`Rat("Rat").sound()` печатает `Животное Rat звуки`. Запись `super.sound()` выбирает реализацию родителя; вызов `sound()` из тела самого переопределённого метода снова вызвал бы этот метод и привёл к рекурсии.

В исходнике `Dog.sound()` сначала печатает `Гав-гав`, затем вызывает унаследованный `doSmt()`, который выводит `fasf`. Переопределять все `open`-методы необязательно: готовую реализацию можно унаследовать. Добавленный `Animal.eat()` возвращает `true`, но в `main()` этого урока не вызывается.

## Абстрактные классы

**Абстрактный класс** нельзя создать непосредственно. Он может содержать общие реализованные методы и абстрактные методы, которые обязан реализовать конкретный наследник.

```kotlin
abstract class Humanoid {
    fun talkAnything() = println("Звук")
    abstract fun move()
}

class Zombie : Humanoid() {
    override fun move() = println("Двигается как зомби")
}
```

Наследник получает готовый `talkAnything` и предоставляет реализацию `move`. Прямой вызов `Humanoid()` недопустим.

### Геометрические фигуры из Lesson 4.kt

В репозитории общий тип `Shape` хранит имя, реализует `describe()` и требует от наследников вычислять площадь и периметр. Сокращённая запись того же примера:

```kotlin
import kotlin.math.PI

abstract class Shape(val name: String) {
    abstract fun area(): Double
    abstract fun perimeter(): Double
    fun describe(): String = name
}

class Circle(val radius: Double, name: String) : Shape(name) {
    override fun area(): Double = PI * radius * radius
    override fun perimeter(): Double = 2 * PI * radius
}

class Square(val width: Double, name: String) : Shape(name) {
    override fun area(): Double = width * width
    override fun perimeter(): Double = 4 * width
}
```

| Объект из урока | `area()` | `perimeter()` | `describe()` |
| --- | --- | --- | --- |
| `Circle(10.0, "Круг")` | примерно `314.1592653589793` | примерно `62.83185307179586` | `Круг` |
| `Square(5.0, "Квадрат")` | `25.0` | `20.0` | `Квадрат` |

`PI` импортируется из `kotlin.math`. Абстрактные методы объявлены без тела; конкретный наследник обязан реализовать их либо сам оставаться абстрактным. Абстрактный класс может иметь конструктор, свойства и готовые методы, как `Shape.describe()`. Поэтому комментарий исходника «абстрактный класс не имеет реализации» следует понимать как неточную формулировку: без реализации здесь именно абстрактные члены. См. [абстрактные классы](https://kotlinlang.org/docs/classes.html#abstract-classes).

## Интерфейсы и реализация по умолчанию

**Интерфейс** задаёт контракт поведения; его методы могут быть объявлены без тела или иметь реализацию по умолчанию.

```kotlin
interface Moveable {
    fun move()
    fun run() = println("Что-то умеет бегать")
}

open class Animal(val typeName: String) : Moveable {
    override fun move() = println("Животное $typeName двигается")
    override fun run() = println("Животное бежит")
}

class Robot(val name: String) : Moveable {
    override fun move() = println("Робот $name двигается")
}

fun moveInGame(item: Moveable) {
    item.move()
    item.run()
}
```

`Robot` реализует обязательный `move` и использует готовый `run`. `Animal` переопределяет оба метода. Одна функция `moveInGame` работает с обоими типами через общий контракт.

В примере полёта интерфейс может требовать `fly()` и предоставлять готовый `land()`. Метод с телом не обязательно переопределять, метод без тела нужно реализовать в конкретном классе.

Класс может наследовать один класс и реализовать несколько интерфейсов: `class Bird(...) : Animal(...), Flyable, Swimmable`. Состояние и общий код размещают в базовом классе, отдельные способности описывают интерфейсами.

В репозитории соответствующая строка — `class Bird(val name: String) : NewAnimal(name), Flyable, Swimable`. Имя `Swimable` в исходнике написано с одной `m`. `Bird` реализует `fly()`, `land()` и `swim()`, а `Human` — `fly()` и `land()`. Интерфейс `Flyable` уже содержит тело `land()`, поэтому переопределение этого метода — выбор автора, а не обязательное требование.

Параметр `name` у `NewAnimal(name: String)` без `val` или `var` не создаёт хранимое свойство. Собственное свойство птицы задаёт именно `val name` в конструкторе `Bird`. Интерфейс может объявлять свойства и их вычисляемые геттеры, но не имеет собственных полей для хранения состояния.

### Совпадающие методы нескольких интерфейсов

В уроке `A` содержит реализацию метода, а `B` требует метод с той же сигнатурой. Класс `C` явно выбирает реализацию:

```kotlin
interface A {
    fun doSomething() = println("doSomething")
}

interface B {
    fun doSomething()
}

class C : A, B {
    override fun doSomething() {
        super<A>.doSomething()
    }
}
```

Вызов `C().doSomething()` печатает `doSomething`. `super<A>` уточняет интерфейс, чьё готовое тело нужно вызвать. Вызвать `super<B>.doSomething()` здесь нельзя: у `B` нет реализации. Явное переопределение также требуется, когда несколько интерфейсов предлагают разные реализации одного метода. См. [интерфейсы и разрешение конфликтов](https://kotlinlang.org/docs/interfaces.html#resolving-overriding-conflicts).

## Перегрузка и переопределение

**Перегрузка** — одинаковое имя и разные списки параметров:

```kotlin
fun show(value: String) = println(value)
fun show(value: String, count: Int) = repeat(count) { println(value) }
```

Различие только возвращаемого типа недостаточно. Две функции `fun show(value: String): Int` и `fun show(value: String): String` конфликтуют.

**Переопределение** — новая реализация унаследованного метода с соответствующей сигнатурой. Оно использует `override` и связано с отношением наследования.

## Data class и поверхностное копирование

`data class` предназначен для хранения данных и автоматически получает стандартное сравнение по свойствам первичного конструктора, строковое представление и `copy`.

```kotlin
class NumberHolder(var n: Int = 0)
data class PersonData(val name: String, var age: Int, val holder: NumberHolder)

val original = PersonData("Иван", 18, NumberHolder())
val copied = original.copy()
original.age = 20
println(copied.age) // 18
original.holder.n = 100
println(copied.holder.n) // 100
```

`copy()` — **поверхностная копия**. Значения свойств копируются, но вложенный объект `holder` остаётся общим. Для независимого вложенного состояния его копируют отдельно.

### Point: сравнение значений и ссылок

Пример из репозитория задаёт точку через `data class Point(val x: Double, val y: Double)`. Для такого класса компилятор генерирует `equals()` и `hashCode()`, `toString()`, `copy()` и функции `component1()`/`component2()` для деструктуризации.

```kotlin
data class Point(val x: Double, val y: Double)

val point1 = Point(10.0, 20.0)
val point2 = Point(-10.0, 42.0)
val sameCoordinates = Point(10.0, 20.0)
val alias = point1

println(point1)                   // Point(x=10.0, y=20.0)
println(point1 == point2)         // false
println(point1 === point2)        // false
println(point1 === point1)        // true
println(point1 == sameCoordinates)  // true
println(point1 === sameCoordinates) // false
println(point1 === alias)         // true

val moved = point1.copy(x = 15.0)
val (x, y) = point1
```

`==` проверяет равенство через `equals`; для этого `data class` — совпадение координат. `===` проверяет, ссылаются ли переменные на один и тот же объект. В исходном примере обе проверки разных точек дают `false`, поэтому одинаковые координаты у двух отдельных объектов лучше показывают различие операторов.

`moved` — новая точка `(15.0, 20.0)`, а исходная остаётся прежней. В `val (x, y) = point1` переменные получают `10.0` и `20.0`. При стандартной генерации методов учитываются свойства **первичного конструктора**; дополнительные свойства из тела класса в такое сравнение не входят. См. [data classes](https://kotlinlang.org/docs/data-classes.html).

## Enum, object и companion object

**Enum** задаёт ограниченный набор именованных значений:

```kotlin
enum class Color(val hex: String) {
    RED("#ff0000"), GREEN("#00ff00"), BLUE("#0000ff")
}
```

**`object`** объявляет единственный объект, к которому обращаются по имени:

```kotlin
object GameManipulator {
    var gamersCount = 10
}
```

**`companion object`** размещает члены, доступные через имя содержащего класса:

```kotlin
class Calculator {
    companion object {
        fun sum(a: Int, b: Int) = a + b
    }
}
println(Calculator.sum(1, 2))
```

Эти конструкции решают разные задачи: перечисление вариантов, единственный объект и связанные с классом операции.

### OrderState: возврат нового состояния

В репозитории перечисление `OrderState` хранит строковое свойство `value` и метод перехода. Тот же метод можно записать как выражение:

```kotlin
enum class OrderState(val value: String) {
    NEW("new"),
    PAID("paid"),
    DELIVERED("delivered"),
    CANCELLED("cancelled");

    fun changeState(state: OrderState): OrderState = when (state) {
        NEW -> PAID
        PAID -> DELIVERED
        DELIVERED -> CANCELLED
        CANCELLED -> NEW
    }
}
```

Точка с запятой отделяет список констант от методов. `OrderState.NEW` — значение перечисления, `OrderState.NEW.value` — строка `"new"`. Все варианты учтены в `when`, поэтому `else` не требуется.

Метод выбирает переход по **переданному аргументу `state`**, а не по объекту слева от точки. Вызов из урока `orderState.changeState(OrderState.DELIVERED)` возвращает `CANCELLED`, даже если `orderState` равен `NEW`.

```kotlin
val orderState = OrderState.NEW
val result = orderState.changeState(OrderState.DELIVERED)
println(orderState) // NEW
println(result)     // CANCELLED

var current = OrderState.NEW
current = current.changeState(current)
println(current)   // PAID
```

Сам вызов не переприсваивает переменную. В исходном `main()` возвращённое значение не сохраняется и не печатается, поэтому `orderState` остаётся `NEW`. Для изменения переменной в примере выше нужны `var` и явное присваивание результата. См. [enum classes](https://kotlinlang.org/docs/enum-classes.html).

## Модули и internal

В репозитории, помимо основного модуля, есть модули `Data` и `UI`. Основной модуль подключает оба как зависимости; это видно в [Lesson-1.iml](https://github.com/docfr10/Lesson-1/blob/f4b3824eef4ca68610f8ed748ab494f53582b1ac/Lesson-1.iml).

```kotlin
// Data/src/Main.kt — модуль Data
internal class Data1 {
    fun showData() = println("Show Data")
}

// UI/src/Main.kt — модуль UI
class UI {
    fun showUI() = println("Show UI")
}
```

Это фрагменты **разных файлов и модулей**. Класс `UI` имеет видимость `public` по умолчанию, поэтому доступен в основном модуле. Класс `Data1` помечен `internal`: создать его можно внутри модуля `Data`, но нельзя напрямую из основного модуля, даже при наличии зависимости на `Data`. Именно поэтому строка `val data = Data1()` в `Lesson 4.kt` закомментирована.

`val ui = UI()` создаёт объект, но не вызывает `showUI()` и ничего не печатает. Для вывода `Show UI` нужен отдельный вызов `ui.showUI()`.

Модуль — набор Kotlin-файлов, компилируемых вместе, например модуль IntelliJ IDEA или набор исходников Gradle. Это граница, отличная от файла и пакета: `internal` разрешает доступ из других файлов того же модуля, а верхнеуровневый `private` ограничивает доступ своим файлом. Модификатор `protected` применяют к членам класса, а не к верхнеуровневым объявлениям. См. [области видимости](https://kotlinlang.org/docs/visibility-modifiers.html#modules).

## Главное

- Функции высшего порядка принимают или возвращают функции; замыкания удерживают внешние переменные.
- Условия начального состояния проверяют в `init`; сеттер не проверяет инициализатор автоматически.
- `lateinit` откладывает присваивание, `lazy` — вычисление до первого чтения.
- Переопределённый метод выбирается по фактическому объекту.
- Интерфейс задаёт контракт и может предоставлять готовое поведение.
- Перегрузка различается параметрами, а не только типом результата.
- `data class.copy()` не копирует вложенные объекты рекурсивно.
- `super.method()` вызывает готовую реализацию родителя; `super<Interface>.method()` выбирает конкретный интерфейс.
- Абстрактный класс может содержать состояние и готовые методы; экземпляр создают через конкретного наследника.
- Для `Point` оператор `==` сравнивает координаты, а `===` — тождественность объектов.
- Возвращённое состояние enum нужно сохранить явно: один вызов `changeState` не меняет переменную.
- `internal` ограничивает доступ модулем, даже если другие модули подключили его как зависимость.
