## Что изучается на занятии

**Тема: несколько экранов Android-приложения, передача данных и фрагменты.** Конспект подготовлен по изменениям [Lesson 9, коммит `faa9bb1`](https://github.com/docfr10/LessonAndroidStart/commit/faa9bb1), от **03.11.2026**, относительно предыдущего занятия. Это разбор исходного кода: сборка и запуск приложения не проверялись.

В проект добавлена `MainActivity2`. Нажатие на изображение первого экрана создаёт явный `Intent`, передаёт текст поля ввода и открывает второй экран. Вторая Activity выводит полученную строку и содержит `BlankFragment` с собственной разметкой.

| Файл | Назначение |
|---|---|
| `AndroidManifest.xml` | объявление второй Activity |
| `MainActivity.kt` | обработчик нажатия, создание `Intent` и передача строки |
| `MainActivity2.kt` | создание второго экрана и чтение строки |
| `activity_main2.xml` | разметка второго экрана и контейнер фрагмента |

| `app/build.gradle.kts`, `gradle/libs.versions.toml` | зависимость AndroidX Fragment |

## Вторая Activity и манифест

**Activity** — компонент Android, управляющий окном приложения. Для нового экрана создан класс `MainActivity2 : AppCompatActivity()`. Его нужно не только написать, но и объявить в [манифесте](https://github.com/docfr10/LessonAndroidStart/blob/faa9bb1/app/src/main/AndroidManifest.xml):

```xml
<activity
    android:name=".MainActivity2"
    android:exported="false"
    android:windowSoftInputMode="adjustResize" />
```

`android:name` указывает класс компонента. `exported="false"` означает, что его нельзя запускать непосредственно из других приложений; запуск из собственного приложения возможен. `adjustResize` задаёт режим обработки окна при появлении экранной клавиатуры; результат зависит также от обработки системных отступов.

Стартовой остаётся `MainActivity`: именно у неё в манифесте фильтр `MAIN` и `LAUNCHER`. `MainActivity2` не становится стартовой только из-за объявления. Ранее существовавший в файле `MainActivity.kt` класс `SecondActivity` — отдельный учебный пример, а не добавленная здесь вторая Activity.

## Переход с помощью Intent

**Intent** описывает намерение выполнить действие. В данном случае явно указан класс получателя, поэтому это *явный Intent*. Код из [`MainActivity.kt`](https://github.com/docfr10/LessonAndroidStart/blob/faa9bb1/app/src/main/java/com/example/lessonandroidstart/MainActivity.kt):

```kotlin
binding.imageView.setOnClickListener {
    val intent = Intent(this, MainActivity2::class.java).apply {
        putExtra("value", binding.editTextTextEmailAddress.text.toString())
    }
    startActivity(intent)
}
```

Последовательность действий:

1. Пользователь вводит текст в поле и нажимает **`imageView`**, а не `imageButton`.
2. `Intent(this, MainActivity2::class.java)` создаёт намерение открыть `MainActivity2`; `this` здесь — текущая Activity.
3. `putExtra("value", ...)` добавляет строку под ключом `value`. `text.toString()` преобразует содержимое поля в `String`.
4. `startActivity(intent)` передаёт намерение системе и запускает экран.

`apply` возвращает тот же объект после выполнения блока его настройки. Аналогичный учебный вариант без `apply`:

```kotlin
val nextScreen = Intent(this, MainActivity2::class.java)
nextScreen.putExtra("value", binding.editTextTextEmailAddress.text.toString())
startActivity(nextScreen)
```

Передаётся снимок текста в момент нажатия, а не общая изменяемая ссылка на поле. Нажатие не проверяет, что введён адрес электронной почты: будет передана и пустая строка.

## Получение переданных данных

В [`MainActivity2.kt`](https://github.com/docfr10/LessonAndroidStart/blob/faa9bb1/app/src/main/java/com/example/lessonandroidstart/MainActivity2.kt) экран устанавливается и после этого ищется текстовый элемент:

```kotlin
setContentView(R.layout.activity_main2)
val textView = findViewById<TextView>(R.id.textView2)
textView.text = intent.getStringExtra("value")
```

Свойство `intent` содержит намерение, с которым запущена Activity. `getStringExtra("value")` читает строку с тем же ключом, что использован в `putExtra`. Если дополнения нет или оно не соответствует ожидаемому строковому типу, результат может быть `null`. В учебном коде значение присваивается напрямую, без отдельной обработки отсутствующих данных.

Для более устойчивого варианта можно задать значение по умолчанию и вынести ключ в константу, общую для отправителя и получателя:

```kotlin
const val EXTRA_VALUE = "value"

// В получающей Activity:
textView.text = intent.getStringExtra(EXTRA_VALUE) ?: "Нет данных"
```

Это дополнение для понимания, а не точная копия проекта. Одинаковое написание ключа в обеих Activity важно: опечатка приведёт к отсутствующему значению. Для больших или чувствительных данных не стоит рассматривать extras как универсальное хранилище: их назначение — передача небольших данных между компонентами.

## Разметка второго экрана

В `onCreate` вторая Activity вызывает `enableEdgeToEdge()`, устанавливает `activity_main2` и применяет системные отступы к корневому `main`. Через `setPadding` содержимое отодвигается от системных панелей.

Корень [`activity_main2.xml`](https://github.com/docfr10/LessonAndroidStart/blob/faa9bb1/app/src/main/res/layout/activity_main2.xml) — `ConstraintLayout`. Внутри находятся `TextView` для переданной строки, два `LinearLayout` и `FragmentContainerView`.

**LinearLayout** располагает дочерние элементы последовательно по одной оси:

| Контейнер | `orientation` | Дочерние элементы |
|---|---|---|
| Первый | `horizontal` | `TextView`, `Switch`, `Button` |
| Второй | `vertical` | `CheckBox`, `Switch` |

У элементов первого контейнера одинаковый `layout_weight="1"`: вес участвует в распределении оставшегося пространства по горизонтальной оси. Поскольку ширина элементов задана как `wrap_content`, первоначальные размеры по содержимому тоже влияют на результат; одинаковые веса сами по себе не гарантируют равную итоговую ширину. Для равных долей в типичном примере задают `layout_width="0dp"` и одинаковый вес. В коде второй Activity обработчики этих новых переключателей и кнопки не добавлены.

В проекте у контейнеров и изображения фиксированные размеры в `dp`. Разметку стоит проверить на разных экранах и при увеличенном шрифте: фиксированные размеры могут привести к тесноте или обрезанию.

## Фрагмент внутри Activity

**Fragment** — управляемая часть интерфейса и поведения, размещаемая внутри Activity. В проект добавлены зависимость `androidx.fragment` и класс [`BlankFragment`](https://github.com/docfr10/LessonAndroidStart/blob/faa9bb1/app/src/main/java/com/example/lessonandroidstart/BlankFragment.kt). За экземпляры и их состояние отвечает `FragmentManager` принимающей Activity.

Фрагмент создаёт своё представление в `onCreateView`:

```kotlin
override fun onCreateView(
    inflater: LayoutInflater,
    container: ViewGroup?,
    savedInstanceState: Bundle?
): View? {
    return inflater.inflate(R.layout.fragment_blank, container, false)
}
```

`inflater` создаёт дерево `View` из XML, `container` — предполагаемый родитель, а `false` означает, что при создании разметку не нужно сразу присоединять к нему вручную. Фреймворк размещает возвращённое представление фрагмента. `onCreate` в этом классе лишь вызывает реализацию родителя и собственной логики не добавляет.

В разметке Activity контейнер объявляет класс фрагмента:

```xml
<androidx.fragment.app.FragmentContainerView
    android:id="@+id/fragmentContainerView"
    android:name="com.example.lessonandroidstart.BlankFragment"
    android:layout_width="294dp"
    android:layout_height="238dp" />
```

Это сокращённый фрагмент XML без ограничений расположения. `android:name` позволяет создать указанный фрагмент при создании контейнера; отдельной транзакции в `MainActivity2` для него нет. Разметка [`fragment_blank.xml`](https://github.com/docfr10/LessonAndroidStart/blob/faa9bb1/app/src/main/res/layout/fragment_blank.xml) содержит `ImageView` со встроенным изображением Android. Сам фрагмент не объявляется в манифесте как Activity.

У фрагмента есть собственный жизненный цикл и отдельный жизненный цикл его представления. Например, представление может быть уничтожено до уничтожения самого фрагмента. При использовании View Binding во фрагменте это важно учитывать и освобождать ссылку на binding в `onDestroyView`.

## Жизненный цикл и возврат назад

При обычном переходе новая Activity попадает поверх предыдущей в стек задачи. Система отправляет первой Activity события приостановки и, когда она становится невидимой, остановки; вторая создаётся и становится активной. При системном возврате предыдущая Activity обычно снова показывается. Точный порядок и набор событий зависят от состояния и поведения системы, поэтому лучше наблюдать их в Logcat, а не считать любой переход уничтожением первого экрана.

Значение, переданное через `Intent`, читается второй Activity; обратная передача результата в этом примере не реализована. Изменение надписи на втором экране само по себе не меняет поле ввода первого.

## Особенности учебного примера

- Варианты разметки и большие фиксированные размеры следует проверять на устройстве; фрагмент с картинкой высотой `314dp` находится в контейнере высотой `238dp`, поэтому возможна обрезка содержимого.
- `hello_blank_fragment` добавлен в строковые ресурсы как шаблонная строка, но показанная разметка фрагмента её не использует. У `button_text` убран `translatable="false"`, что согласуется с наличием перевода.
- У интерактивного изображения желательно задать понятное описание действия и проверить доступность с TalkBack; смысл нажатия должен быть понятен без догадок.
- Версия зависимости Fragment в снимке — `1.9.1`. Это настройка данного учебного проекта, а не требование для всех приложений.

## Главное

1. Экран `MainActivity2` объявляется в манифесте, а `MainActivity` остаётся точкой входа.
2. Явный `Intent` задаёт класс получателя; `putExtra` передаёт значение, `startActivity` запускает экран.
3. `getStringExtra` читает данные по тому же ключу и может вернуть `null`.
4. `LinearLayout` размещает элементы по горизонтали или вертикали; вес распределяет свободное пространство.
5. `FragmentContainerView` содержит фрагмент, который создаёт собственное дерево интерфейса в `onCreateView`.
