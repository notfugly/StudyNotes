# C++: особенности жизненного цикла объектов

**Дата занятия:** 23.10.2026.

**Тема:** исключения в конструкторах и деструкторах, частичное конструирование.

## Жизненный цикл объекта и инвариант

При работе с объектом класса нужно различать **память для объекта**, **его инициализацию** и **разрушение**.

Для обычного объекта класса с пользовательским конструктором последовательность выглядит так:

1. Предоставляется память подходящего размера и выравнивания.
2. Инициализируются базовые подобъекты и поля.
3. Выполняется тело конструктора.
4. После успешного конструирования объект используется.
5. Вызывается деструктор, затем уничтожаются поля и базы.
6. Память освобождается или становится доступной для другого использования согласно способу её получения.

Это практическая схема: формальные правила времени жизни объектов содержат специальные случаи для тривиальных типов, объединений и повторного использования памяти.

**Инвариант класса** — условие, которое должно выполняться для корректно созданного объекта и сохраняться его публичными операциями. Например, размер буфера неотрицателен, а файловый объект владеет допустимым дескриптором.

**Задача конструктора — установить инвариант.** Если обязательные условия выполнить нельзя, конструктор может выбросить исключение.

```cpp
#include <stdexcept>

class Positive {
    int value_;

public:
    explicit Positive(int value) : value_(value) {
        if (value <= 0) {
            throw std::invalid_argument("value must be positive");
        }
    }

    int value() const noexcept { return value_; }
};
```

При попытке `Positive x(0);` управление переходит к обработчику исключения. Успешно созданной переменной `x`, с которой можно продолжить обычную работу, не появляется.

Возвращаемого значения у конструктора нет, поэтому вернуть код ошибки через `return -1;` нельзя. Альтернативой исключениям может быть фабрика, возвращающая результат или описание ошибки, но это уже другой интерфейс создания объекта.

## Порядок конструирования и разрушения

### Порядок инициализации

Для неделегирующего конструктора порядок фиксирован языком:

1. **Виртуальные базы**, если создаётся самый производный объект. Они обходятся в глубину слева направо по графу наследования и создаются по одному разу.
2. **Прямые невиртуальные базы** в порядке их перечисления в объявлении класса.
3. **Нестатические поля** в порядке их объявления внутри класса.
4. **Тело конструктора**.

**Порядок записей в списке инициализации не меняет порядок создания полей и баз.**

```cpp
struct Example {
    int first;
    int second;

    Example() : second(20), first(10) {}
};
```

Сначала инициализируется `first`, затем `second`. Для читаемости список следует писать в том же порядке, что и объявления.

Особенно опасны зависимости между полями:

```cpp
struct WrongOrder {
    int copy;
    int original;

    // Ошибка: original ещё не инициализирован при чтении.
    WrongOrder() : original(10), copy(original) {}
};
```

Исправление — объявить `original` раньше `copy` и так же расположить инициализаторы. Нельзя рассчитывать на осмысленное значение ещё не инициализированного `int`.

### Порядок разрушения

При нормальном уничтожении полностью созданного объекта:

1. Выполняется тело деструктора.
2. Уничтожаются поля в обратном порядке объявления.
3. Уничтожаются прямые невиртуальные базы в обратном порядке.
4. Для самого производного объекта уничтожаются виртуальные базы в обратном порядке их создания.

Локальные переменные тела деструктора уничтожаются при выходе из его тела, до последующего уничтожения полей и баз.

**Деструктор не заканчивается на последней строке написанного пользователем тела:** после неё язык автоматически выполняет разрушение подобъектов.

## Исключение в конструкторе

### Где может возникнуть исключение

Инициализация может прерваться:

- при вычислении аргумента инициализатора;
- в конструкторе базы;
- в конструкторе поля;
- в инициализаторе поля по умолчанию;
- в теле конструктора.

Если исключение возникает **при вычислении аргументов перед вызовом конструктора**, сам конструктор ещё не начался. Такой сбой нужно отличать от исключения внутри инициализации объекта.

### Основное правило

Если обычный **неделегирующий конструктор** завершился исключением:

- деструктор создаваемого объекта **не вызывается**;
- уже полностью созданные поля и базы уничтожаются автоматически;
- подобъекты уничтожаются в обратном порядке завершения их создания;
- для поля или базы, чей конструктор выбросил исключение, их собственный деструктор не вызывается;
- ещё не начатые инициализации не выполняются.

При этом у самого неудачно создаваемого поля могут быть собственные успешно созданные поля и базы. Они также очищаются по этому правилу. **Откат происходит на каждом уровне вложенности.**

### Почему не вызывается деструктор всего объекта

Тело деструктора может предполагать, что инвариант уже установлен, а все поля готовы. При частичном конструировании это предположение неверно. Поэтому язык уничтожает только те подобъекты, создание которых действительно завершилось.

Если ошибка возникла в теле конструктора, поля и базы к этому моменту уже инициализированы. Они будут уничтожены, но деструктор всего объекта всё равно не вызывается.

**Важно:** автоматическое уничтожение поля-указателя не освобождает объект, на который оно указывает. Для этого нужен владеющий объект, например `std::unique_ptr`.

## Частичное конструирование: подробный пример

**Частичное конструирование** — ситуация, когда инициализация составного объекта уже началась, но завершилась только для части его подобъектов.

```cpp
#include <iostream>
#include <stdexcept>

struct Base {
    Base() { std::cout << "Base()\n"; }
    ~Base() noexcept { std::cout << "~Base()\n"; }
};

struct Part {
    const char* name;

    explicit Part(const char* label, bool fail = false)
        : name(label) {
        std::cout << "Part(" << name << ")\n";
        if (fail) {
            throw std::runtime_error("part construction failed");
        }
    }

    ~Part() noexcept {
        std::cout << "~Part(" << name << ")\n";
    }
};

struct Object : Base {
    Part first;
    Part second;
    Part third;

    Object() : first("first"), second("second", true), third("third") {
        std::cout << "Object body\n";
    }

    ~Object() noexcept { std::cout << "~Object()\n"; }
};

int main() {
    try {
        Object object;
    } catch (const std::exception& error) {
        std::cout << "Caught: " << error.what() << '\n';
    }
}
```

Последовательность сообщений:

```text
Base()
Part(first)
Part(second)
~Part(first)
~Base()
Caught: part construction failed
```

Разбор:

1. `Base` создан полностью.
2. `first` создан полностью.
3. Конструктор `second` начал работу и выбросил исключение.
4. Создание `third` не начинается; тело `Object()` не выполняется.
5. Деструктор `second` не вызывается, потому что его конструирование не завершилось.
6. Уничтожаются `first`, затем `Base`.
7. Деструктор `Object` не вызывается; управление доходит до `catch`.

Само сообщение `Part(second)` означает лишь, что соответствующая строка тела конструктора выполнилась. Оно **не доказывает успешного завершения конструктора**.

Если убрать ошибку из `second` и перенести `throw` в тело `Object()`, перед обработчиком уничтожатся `third`, `second`, `first`, затем `Base`. Сообщения `~Object()` по-прежнему не будет.

## Раскрутка стека

**Раскрутка стека, или stack unwinding,** — уничтожение подходящих автоматических объектов при передаче управления от места выбрасывания исключения к обработчику.

Объекты уничтожаются в порядке, обратном завершению их создания. Объекты во внешних областях видимости, из которых управление не выходит, продолжают существовать.

```cpp
#include <iostream>
#include <stdexcept>

struct Trace {
    const char* name;
    explicit Trace(const char* value) : name(value) {
        std::cout << "+ " << name << '\n';
    }
    ~Trace() noexcept { std::cout << "- " << name << '\n'; }
};

void work() {
    Trace first("first");
    Trace second("second");
    throw std::runtime_error("failure");
}

int main() {
    Trace outer("outer");
    try {
        work();
    } catch (const std::exception&) {
        std::cout << "handler\n";
    }
    std::cout << "after catch\n";
}
```

```text
+ outer
+ first
+ second
- second
- first
handler
after catch
- outer
```

`outer` создан до `try` и не покидает свою область видимости при переходе в `catch`. Он уничтожается позже, при выходе из `main`.

Раскрутка стека вызывает деструкторы объектов-владельцев, но не ищет произвольные ресурсы. Например, для локального `int* p = new int(5);` уничтожение самого указателя не выполняет `delete p`.

Если подходящий обработчик вообще не найден, вызывается `std::terminate`; наличие раскрутки стека до этого вызова определяется реализацией. Поэтому нельзя полагаться на очистку через деструкторы при необработанном исключении.

## Ресурсы и RAII

**RAII, Resource Acquisition Is Initialization,** связывает владение ресурсом с жизненным циклом объекта: получение ресурса устанавливает владение, а деструктор владельца освобождает ресурс.

Ресурсом может быть память, открытый файл, блокировка, сокет или другой объект, требующий парного освобождения.

### Опасный подход: очистка только в деструкторе внешнего класса

```cpp
#include <stdexcept>

class BadBuffer {
    int* data_;

public:
    BadBuffer() : data_(new int[100]) {
        throw std::runtime_error("configuration failed");
    }

    ~BadBuffer() { delete[] data_; }
};
```

Если `new int[100]` выполнен успешно, а затем возникает показанное исключение, буфер теряется:

1. Указатель `data_` получил адрес выделенной памяти.
2. Конструктор `BadBuffer` не завершился.
3. `~BadBuffer()` не вызывается.
4. Указатель сам по себе не выполняет `delete[]`.

### Исправление: ресурс сразу принадлежит полю-владельцу

```cpp
#include <memory>
#include <stdexcept>

class SafeBuffer {
    std::unique_ptr<int[]> data_;

public:
    SafeBuffer() : data_(std::make_unique<int[]>(100)) {
        throw std::runtime_error("configuration failed");
    }
};
```

Поле `data_` успело полностью сконструироваться. При исключении из тела внешнего конструктора вызывается его деструктор, который освобождает массив.

Для обычного динамического массива часто удобнее `std::vector<int>`. По той же причине вместо ручного `lock()` и `unlock()` обычно используют `std::lock_guard` или `std::unique_lock`.

**Каждое успешное получение ресурса должно как можно скорее передавать владение RAII-объекту.** Не следует откладывать эту передачу до конца сложной инициализации.

RAII не означает, что неудачно созданный владелец сам получит вызов своего деструктора. Если конструктор низкоуровневой обёртки получил ресурс, а затем может выбросить исключение, он должен обеспечить очистку через уже созданный внутренний владелец или локальную защиту.

## Ошибка при создании через new

### Обычное выражение new

Выражение `new T(arguments)` объединяет выделение памяти и инициализацию объекта.

Если выделение прошло успешно, но инициализация выбросила исключение, обычное выражение `new` вызывает подходящую функцию освобождения памяти. После этого исключение продолжает распространяться.

```cpp
// Используются определения Object, Base и Part из подробного примера.
Object* pointer = nullptr;

try {
    pointer = new Object;
} catch (const std::exception&) {
    // pointer остаётся nullptr: присваивание не состоялось.
}
```

При обычном `new Object` память **самого `Object`** освобождается, хотя `~Object()` не вызывается. Освобождение памяти и вызов деструктора — разные действия.

Но это не исправит утечку из `BadBuffer`: освобождение блока внешнего объекта не освобождает отдельный массив, адрес которого хранился в его поле.

Для пользовательских перегрузок `operator new` и placement-форм существуют специальные правила поиска соответствующей функции освобождения. Пару выделения и освобождения необходимо проектировать согласованно.

### Что означает new (std::nothrow)

```cpp
#include <new>

// Конструктор T всё ещё может выбросить исключение.
T* pointer = new (std::nothrow) T;
```

В стандартной nothrow-форме **сбой выделения памяти** выражается возвратом `nullptr`. Она не превращает исключение из конструктора `T` в `nullptr`: такое исключение продолжает распространяться.

### Placement new в готовую память

Стандартная форма `new (address) T(...)` создаёт объект в уже предоставленной памяти. Она не получает новый блок памяти.

```cpp
#include <cstddef>
#include <new>

// Используется Object из подробного примера.
alignas(Object) std::byte storage[sizeof(Object)];

try {
    Object* pointer = ::new (static_cast<void*>(storage)) Object;
    pointer->~Object(); // Выполняется только после успешного создания.
} catch (const std::exception&) {
    // При неудачном создании ~Object() вызывать нельзя.
}
```

При сбое конструктора успешно созданные подобъекты очищаются, но стандартная placement-функция освобождения не освобождает предоставленную память. Буфер `storage` остаётся; ответственность за его хранение определяется внешним кодом.

## Частичное создание массива

Элементы массива создаются по возрастанию индекса. Если конструктор очередного элемента выбрасывает исключение:

- уже созданные элементы уничтожаются в обратном порядке;
- деструктор неудачно создаваемого элемента не вызывается;
- следующие элементы не создаются;
- при обычном `new T[n]` освобождается также выделенный для массива блок.

```cpp
#include <iostream>
#include <stdexcept>

struct Item {
    inline static int next_id = 0;
    int id;

    Item() : id(next_id++) {
        std::cout << "+ " << id << '\n';
        if (id == 2) {
            throw std::runtime_error("third element failed");
        }
    }

    ~Item() noexcept { std::cout << "- " << id << '\n'; }
};

int main() {
    try {
        Item items[4];
    } catch (const std::exception&) {
        std::cout << "caught\n";
    }
}
```

```text
+ 0
+ 1
+ 2
- 1
- 0
caught
```

Элемент с `id == 2` не создан полностью, поэтому строки `- 2` нет. Элемент с `id == 3` вообще не начинал создаваться.

Изменение `next_id` не откатывается: это внешнее по отношению к отдельному создаваемому элементу состояние. Автоматическое разрушение подобъектов не отменяет все побочные эффекты конструктора.

## Обработчик function-try-block

### Почему try внутри тела недостаточно

```cpp
class Container {
    Part part_;

public:
    Container() : part_("part", true) {
        try {
            // Этот блок не начинается: исключение возникло раньше.
        } catch (...) {
            // Ошибку инициализации part_ здесь не поймать.
        }
    }
};
```

Перед входом в тело конструктора поля уже инициализируются. Внутренний `try` охватывает только собственный блок.

### Синтаксис function-try-block

**Function-try-block** охватывает и список инициализации, и тело конструктора:

```cpp
#include <stdexcept>

// Используется Part из подробного примера.
class Wrapped {
    Part part_;

public:
    Wrapped() try : part_("part", true) {
        // Тело конструктора.
    } catch (const std::exception&) {
        throw std::runtime_error("cannot construct Wrapped");
    }
};
```

Такой обработчик полезен для преобразования ошибки, добавления контекста или регистрации события. Обычный `throw;` повторно выбрасывает исходное исключение; `throw error;` создаёт новое исключение из выражения и при базовом статическом типе может привести к срезке.

### Ограничения обработчика конструктора

1. До входа в обработчик уже выполнено уничтожение успешно созданных подобъектов.
2. Обращение к нестатическим полям или базам создаваемого объекта в таком обработчике приводит к **неопределённому поведению**. Нельзя читать поле даже «только для сообщения об ошибке».
3. Параметры конструктора доступны, но нужно учитывать их фактическое состояние, например возможное предыдущее перемещение из них.
4. `return;` в обработчике function-try-block конструктора запрещён.
5. Если обработчик просто достигает конца, исходное обрабатываемое исключение автоматически выбрасывается повторно.

**Function-try-block конструктора не позволяет подавить ошибку и получить успешно созданный объект.** Восстанавливать допустимое состояние нужно в обычной логике инициализации, до необратимого выхода из конструктора по исключению.

### Function-try-block деструктора

Он способен охватить ошибки из тела деструктора и разрушения его подобъектов. Но при достижении конца обработчика деструктора исключение тоже автоматически выбрасывается повторно.

В отличие от конструктора, `return;` в таком обработчике деструктора допустим и завершает его без повторного выбрасывания. Однако подобъекты уже разрушены, обращаться к ним нельзя. Для обычной обработки ошибок отдельной операции очистки проще использовать `try` внутри тела деструктора и владельцев с невыбрасывающими деструкторами.

## Делегирующие конструкторы

**Делегирующий конструктор** поручает первоначальное создание объекта другому конструктору того же класса.

```cpp
#include <iostream>
#include <stdexcept>

struct Delegated {
    explicit Delegated(int) {
        std::cout << "target constructor\n";
    }

    Delegated() : Delegated(1) {
        std::cout << "delegating body\n";
        throw std::runtime_error("failure after delegation");
    }

    ~Delegated() noexcept {
        std::cout << "~Delegated\n";
    }
};

int main() {
    try {
        Delegated object;
    } catch (const std::exception&) {
        std::cout << "caught\n";
    }
}
```

```text
target constructor
delegating body
~Delegated
caught
```

**Особое правило:** если целевой конструктор успешно завершился, а тело делегирующего затем вышло по исключению, вызывается деструктор объекта.

Если же исключение возникло в самом целевом неделегирующем конструкторе, действуют обычные правила частичного конструирования: деструктор всего объекта не вызывается.

| Место ошибки | Вызывается ли деструктор всего объекта? |
|---|---|
| Инициализация базы или поля неделегирующим конструктором | Нет |
| Тело неделегирующего конструктора | Нет |
| Тело делегирующего конструктора после успешного завершения целевого | Да |

## Исключения в деструкторах и noexcept

### Смысл noexcept

```cpp
void cleanup() noexcept;
void risky_operation() noexcept(false);
```

`noexcept` означает `noexcept(true)`: исключение не должно покинуть функцию. `noexcept(false)` разрешает распространение исключения, но не утверждает, что функция обязательно его выбросит.

Внутри `noexcept`-функции можно вызывать потенциально выбрасывающие операции и перехватывать их ошибки. **Нарушение происходит, когда исключение должно выйти за границу функции**, а не просто при выполнении `throw` внутри неё.

Если исключение покидает `noexcept`-функцию, вызывается `std::terminate`. Внешний `catch` не сможет перехватить его обычным образом.

### Неявная спецификация деструктора

У деструктора без явно указанного `noexcept` спецификация выводится по специальным правилам для деструкторов, с учётом соответствующих деструкторов полей и баз. Для обычного класса, подобъекты которого имеют невыбрасывающие деструкторы, результат — `noexcept(true)`.

```cpp
struct Ordinary {
    ~Ordinary() {} // В этом классе неявно noexcept(true).
};

struct Risky {
    ~Risky() noexcept(false) {}
};

struct ContainsRisky {
    Risky member;
    ~ContainsRisky() {} // Потенциально выбрасывающий деструктор.
};
```

Тело пользовательского деструктора не анализируется для вывода «может ли он бросить». Если добавить в тело `~Ordinary()` неперехваченное исключение, это не превратит его автоматически в `noexcept(false)`.

Спецификацию можно проверить оператором `noexcept` без выполнения выражения:

```cpp
#include <utility>

static_assert(noexcept(std::declval<Ordinary&>().~Ordinary()));
static_assert(!noexcept(std::declval<ContainsRisky&>().~ContainsRisky()));
```

### Потенциально выбрасывающий деструктор при обычном выходе

Сам язык позволяет написать `~T() noexcept(false)`. Если такой деструктор выбросил исключение при обычном выходе из области видимости, его может поймать внешний обработчик:

```cpp
#include <iostream>
#include <stdexcept>

struct Throwing {
    ~Throwing() noexcept(false) {
        throw std::runtime_error("destruction failed");
    }
};

int main() {
    try {
        Throwing object;
    } catch (const std::exception&) {
        std::cout << "caught destructor error\n";
    }
}
```

Если тело потенциально выбрасывающего деструктора выходит по исключению, предусмотренные языком оставшиеся вызовы деструкторов полей и баз всё равно выполняются. Если ещё один из этих вызовов завершится исключением во время обработки первого сбоя, произойдёт `std::terminate`.

### Ошибка деструктора во время раскрутки стека

```cpp
// Используется Throwing из предыдущего примера.
try {
    Throwing object;
    throw std::runtime_error("initial error");
} catch (...) {
    // Этот обработчик не спасает от второго исключения,
    // покидающего деструктор во время раскрутки.
}
```

Последовательность:

1. Выбрасывается `initial error`.
2. Для передачи управления в `catch` начинается раскрутка стека.
3. Вызывается `~Throwing()`.
4. Из деструктора выходит другое исключение.
5. Вызывается `std::terminate`.

`noexcept(false)` разрешает выход исключения из функции, но **не отменяет правило завершения программы при сбое очистки во время раскрутки**.

Фраза «любое второе исключение завершает программу» неточна. Внутри деструктора можно выбросить и полностью обработать локальное исключение. Опасно его распространение наружу из вызова очистки, выполняемого механизмом обработки первого исключения.

| Ситуация | Результат |
|---|---|
| Ошибка перехвачена внутри деструктора | Деструктор может завершиться нормально |
| Исключение выходит из `noexcept`-деструктора | `std::terminate` |
| Исключение выходит из `noexcept(false)`-деструктора при обычном выходе | Может быть перехвачено снаружи |
| Исключение выходит из деструктора, вызванного раскруткой стека | `std::terminate` |

## Безопасное проектирование деструктора

**Практическое правило: деструктор освобождает ресурсы и не выпускает исключений наружу.** Операции, ошибка которых важна вызывающему коду, стоит предоставлять отдельными методами.

Пример разделения явного сохранения и автоматического закрытия:

```cpp
#include <fstream>
#include <stdexcept>
#include <string>

class OutputFile {
    std::ofstream stream_;

public:
    explicit OutputFile(const std::string& path) : stream_(path) {
        if (!stream_) {
            throw std::runtime_error("cannot open file");
        }
    }

    void write(const std::string& text) {
        stream_ << text;
        if (!stream_) {
            throw std::runtime_error("write failed");
        }
    }

    void finish() {
        stream_.flush();
        if (!stream_) {
            throw std::runtime_error("flush failed");
        }

        stream_.close();
        if (!stream_) {
            throw std::runtime_error("close failed");
        }
    }

    ~OutputFile() noexcept = default;
};
```

`finish()` вызывается явно там, где ошибку можно обработать. Поле `stream_` автоматически освобождает ресурс при уничтожении объекта, включая выход по исключению. В приведённом интерфейсе после `finish()` запись не предполагается.

Успешные `flush()` и `close()` не означают универсальной гарантии физической записи на носитель: такие гарантии требуют дополнительных средств операционной системы.

Если в деструкторе всё же нужна потенциально выбрасывающая операция:

```cpp
~Resource() noexcept {
    try {
        release();
    } catch (...) {
        report_failure_noexcept();
    }
}
```

Это схема: `release()` и `report_failure_noexcept()` определяются конкретным классом. Обработчик тоже должен быть безопасным: выделение памяти, форматирование или запись в поток внутри него могут сами выбросить исключение.

Перехват ошибки не гарантирует, что ресурс успешно освобождён. Если операция освобождения может отказать, нужно заранее определить политику: повторная попытка, отдельное сообщение об ошибке, регистрация сбоя или осознанное завершение программы.

### std::uncaught_exceptions

Начиная с C++17 функция из `<exception>` возвращает число выброшенных, но ещё не обработанных исключений в текущем потоке:

```cpp
int count = std::uncaught_exceptions();
```

В защитных объектах можно запомнить число при создании и сравнить его с числом при уничтожении. Увеличение помогает определить, что выход связан с новым необработанным исключением. Такой приём используется для выбора между фиксацией действия и откатом.

Но проверка счётчика не делает выбрасывающий деструктор безопасным. Особенно нельзя использовать результат как универсальное разрешение «сейчас можно бросить исключение».

## Гарантии безопасности исключений

**Безопасность исключений** описывает состояние программы после ошибки, а не только наличие `try` и `catch`.

| Гарантия | Что обещает операция |
|---|---|
| Отсутствие гарантий | После ошибки возможны утечки или нарушение инвариантов |
| Базовая | Сохраняются инварианты и отсутствуют утечки; значения могут измениться |
| Строгая | При ошибке наблюдаемое состояние, охваченное контрактом операции, остаётся прежним |
| Невыбрасывающая | Исключения не выходят из операции |

Строгая гарантия подразумевает базовую. Невыбрасывающая гарантия описывает отсутствие выходящих исключений; возможность сообщить об ошибке другим способом определяется контрактом.

Объявление `noexcept` само по себе не обеспечивает корректность: при нарушении обещания вызывается `std::terminate`.

### Что гарантирует частичное конструирование

Язык обеспечивает уничтожение успешно созданных подобъектов. Если каждый ресурс уже имеет корректного владельца, это позволяет избежать утечек при сбое конструктора.

Но автоматически не отменяются:

- изменение глобального счётчика;
- добавление записи во внешний реестр;
- запись данных в файл;
- отправка сетевого сообщения;
- изменения объектов, переданных по ссылке.

Поэтому «конструктор выбросил исключение» не равнозначно «программа полностью вернулась в прежнее состояние».

Для строгой гарантии часто используют схему:

1. Проверить входные данные.
2. Подготовить необходимые ресурсы под управлением локальных владельцев.
3. Выполнить потенциально неудачные вычисления без изменения публикуемого состояния.
4. Зафиксировать результат операцией, которая не выбрасывает исключений.

Откат, если он необходим, тоже должен выполняться безопасно. Нельзя считать строгую гарантию доказанной, если действие по восстановлению само может завершиться исключением.

## Дополнительные особенности жизненного цикла

### Виртуальные функции во время создания и разрушения

При виртуальном вызове для создаваемого или уничтожаемого объекта из конструктора или деструктора используется реализация, соответствующая текущему классу конструктора или деструктора. Переопределение в ещё более производном классе не вызывается.

```cpp
struct BaseView {
    BaseView() { show(); }
    virtual void show() { /* Реализация BaseView. */ }
    virtual ~BaseView() noexcept { show(); }
};

struct DerivedView : BaseView {
    void show() override { /* Реализация DerivedView. */ }
};
```

Вызовы внутри `BaseView()` и `~BaseView()` обращаются к `BaseView::show()`. Поэтому нельзя рассчитывать на готовность производной части объекта из конструктора базы. Виртуальный вызов чисто виртуальной функции для такого объекта из конструктора или деструктора приводит к неопределённому поведению.

### Локальный static при неудачной инициализации

Если динамическая инициализация локальной статической переменной завершается исключением, она не считается завершённой. При следующем проходе через объявление выполняется новая попытка:

```cpp
Widget& instance() {
    static Widget value; // После сбоя следующий вызов повторит попытку.
    return value;
}
```

Это правило относится именно к локальному `static`. Его нельзя переносить на любую глобальную инициализацию. Если исключение покидает динамическую инициализацию нелокальной переменной со статической длительностью хранения, вызывается `std::terminate`.

### Не публиковать неготовый объект

Передача `this` во внешний реестр или запуск работы, которая обращается к объекту ещё до завершения конструктора, требуют особой осторожности. Если дальнейшая инициализация завершится исключением, внешний код может сохранить ссылку на объект, который так и не был успешно создан.

Безопаснее завершить создание и только затем выполнять внешнюю регистрацию или запуск, например через фабрику. При необходимости регистрации внутри конструктора нужен надёжный откат регистрации.

## Алгоритм разбора и типичные ошибки

### Как определить, какие деструкторы вызываются

1. Выписать фактический порядок создания баз и полей по объявлениям.
2. Найти точку возникновения исключения.
3. Отметить только объекты, чьё конструирование завершилось успешно.
4. Уничтожить покидаемые локальные объекты и созданные подобъекты в обратном порядке.
5. Проверить, является ли конструктор делегирующим и завершился ли целевой конструктор.
6. Отдельно определить судьбу памяти: обычное `new`, placement new или автоматическое хранение.
7. Проверить, не выходит ли ещё одно исключение из очистки и не нарушается ли `noexcept`.
8. Найти обработчик; при его отсутствии учитывать `std::terminate`.

### Частые ошибки

| Ошибочное представление | Корректное правило |
|---|---|
| «Деструктор внешнего класса очистит всё после сбоя конструктора» | При обычном неудачном конструировании он не вызывается; нужны владельцы ресурсов |
| «Поля создаются в порядке списка инициализации» | Порядок определяется объявлениями полей |
| «Если тело конструктора началось, весь объект уже успешно создан» | Конструирование может ещё завершиться исключением |
| «Сырой указатель автоматически освобождает выделенную память» | Указатель хранит адрес; владение нужно реализовать отдельно |
| «Внешний catch перехватит любое исключение деструктора» | Нарушение `noexcept` или сбой очистки при раскрутке приводят к `std::terminate` |
| «noexcept запрещает писать throw внутри функции» | Запрещён выход исключения за её границу |
| «nothrow-new подавляет исключения конструктора» | Оно меняет стандартное поведение при отказе выделения памяти |
| «catch конструктора может восстановить уже разрушенные поля» | В function-try-block обращаться к ним нельзя, а успешное завершение конструктора из обработчика невозможно |
| «Частичное конструирование отменяет все побочные эффекты» | Автоматически уничтожаются подобъекты; внешнее состояние требует отдельного решения |

## Задачи для самопроверки

### Задача 1. Ошибка во втором поле

У класса `D` есть база `B` и поля `x`, `y`, `z`, объявленные в таком порядке. Конструктор `y` выбрасывает исключение. Все деструкторы невыбрасывающие. Какие деструкторы выполнятся?

**Ответ:** деструктор `x`, затем `B`. Деструкторы `y`, `z` и `D` не вызываются. Если у `y` есть собственные полностью созданные подобъекты, сначала выполняется их очистка.

### Задача 2. Ошибка в теле конструктора

У того же класса все поля созданы, но исключение возникло в теле обычного неделегирующего конструктора `D`.

**Ответ:** сначала очищаются созданные локальные объекты тела, затем поля `z`, `y`, `x`, затем база `B`. Деструктор `D` не вызывается.

### Задача 3. Сырой указатель и unique_ptr

Конструктор сначала получает массив, затем создаёт второе поле, конструктор которого может выбросить исключение. Когда массив не потеряется?

**Ответ:** если к моменту сбоя массив уже принадлежит полностью созданному RAII-полю, например `std::unique_ptr<int[]>`. Одного поля `int*` и освобождения в деструкторе внешнего класса недостаточно.

### Задача 4. Деструктор noexcept(false)

Деструктор объявлен `noexcept(false)` и выбрасывает исключение. Всегда ли оно доходит до внешнего `catch`?

**Ответ:** нет. При обычном выходе оно может быть поймано. Если деструктор вызван механизмом раскрутки стека и исключение выходит из него, вызывается `std::terminate`.

### Задача 5. Обработчик конструктора

Что произойдёт, если обработчик function-try-block конструктора напечатает сообщение и достигнет закрывающей скобки?

**Ответ:** обрабатываемое исключение будет выброшено повторно. Успешного завершения конструктора не произойдёт.

### Задача 6. Делегирование

Конструктор `D()` делегирует в `D(10)`. Целевой конструктор завершился успешно, затем тело `D()` выбросило исключение.

**Ответ:** вызывается `~D()`. Это специальный случай, который нужно отличать от ошибки в обычном неделегирующем конструкторе.

## Главное

- **Успешное выделение памяти не означает успешного создания объекта.** Инициализация может завершиться исключением.
- **При сбое неделегирующего конструктора деструктор всего объекта не вызывается.** Уже созданные подобъекты очищаются в обратном порядке.
- **Порядок создания определяется объявлениями баз и полей.** Порядок записей списка инициализации его не меняет.
- **RAII защищает ресурсы при частичном конструировании и раскрутке стека.** Сырой указатель сам по себе ресурс не освобождает.
- **Обычное new освобождает память внешнего объекта при сбое его конструктора.** Это не исправляет утечки отдельных ресурсов внутри него.
- **Function-try-block охватывает инициализаторы и тело конструктора.** Его обработчик не может превратить неудачное создание в успешное.
- **После успешного целевого конструктора сбой тела делегирующего вызывает деструктор объекта.** Это важное исключение из общего правила.
- **Деструктор должен завершаться без выходящего исключения.** Нарушение `noexcept` и сбой очистки во время раскрутки приводят к `std::terminate`.
- **Ошибки важных завершающих операций следует сообщать через явные методы.** Деструктор обеспечивает безопасную автоматическую очистку.
- **Очистка подобъектов не откатывает все внешние изменения.** Строгая гарантия исключений требует отдельного проектирования.
