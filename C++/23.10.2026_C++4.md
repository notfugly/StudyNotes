# Статические и константные члены класса в C++

**Дата занятия:** 23.10.2026  
**Предмет:** C++

## 1. Общая идея: принадлежность и константность

При объявлении члена класса нужно различать два независимых вопроса:

1. **Кому принадлежат данные или операция:** отдельному объекту или классу в целом?
2. **Какие изменения разрешены:** можно ли изменять данные или обращаться к объекту как к изменяемому?

`static` отвечает на первый вопрос, а `const` — на второй. Значение `const` зависит от того, к чему оно относится: к полю, возвращаемому типу или самому методу.

```cpp
class Example {
    int value_ = 0;                   // Свое значение у каждого объекта.
    const int id_;                    // Свое неизменяемое значение.
    inline static int count_ = 0;     // Общая изменяемая переменная, C++17.
    static constexpr int limit_ = 10; // Общая константа.

public:
    explicit Example(int id) : id_(id) {}

    int value() const { return value_; } // Доступ к объекту как к const.
    static int count() { return count_; } // Объект для вызова не нужен.
};
```

| Объявление | Смысл |
| --- | --- |
| `int x;` | Поле каждого отдельного объекта |
| `const int x;` | Константное поле каждого отдельного объекта |
| `static int x;` | Общая переменная класса |
| `static const int x;` | Общая константа класса |
| `int f() const;` | Нестатический метод с константным доступом к объекту |
| `static int f();` | Метод без неявного объекта и без `this` |
| `static int f() const;` | Некорректное объявление |

**Базовое различие:** константное поле и константный метод — разные понятия. Поле `const` нельзя изменять после его инициализации; `const` после списка параметров ограничивает доступ метода к объекту, для которого он вызван.

## 2. Нестатические константные поля

### 2.1. Значение задают при создании объекта

```cpp
class Student {
    const int id_;

public:
    explicit Student(int id) : id_(id) {}

    int id() const {
        return id_;
    }
};
```

У разных объектов могут быть разные значения `id_`:

```cpp
Student first(101);
Student second(202);
```

`const` не означает «одно значение на весь класс». Оно означает запрет изменения соответствующего поля после его инициализации.

### 2.2. Инициализация и присваивание — разные операции

К моменту входа в тело конструктора базовые классы и нестатические поля уже инициализированы. Поэтому значение константного поля задают в списке инициализации или непосредственно в его объявлении.

```cpp
class Point {
    const int x_;
    const int y_ = 0; // Инициализатор поля по умолчанию, C++11.

public:
    explicit Point(int x) : x_(x) {}

    Point(int x, int y) : x_(x), y_(y) {}
};
```

Инициализатор в конкретном конструкторе имеет приоритет над инициализатором поля по умолчанию.

Некорректный подход:

```cpp
class Bad {
    const int x_;

public:
    // Bad(int x) {
    //     x_ = x; // Присваивание, а не инициализация.
    // }
};
```

В таком конструкторе `const int` к тому же остался бы без необходимой инициализации. Для полей классового типа возможна инициализация конструктором по умолчанию, если тип это допускает; затем присвоить новое значение константному полю все равно нельзя.

### 2.3. Порядок инициализации

Нестатические поля инициализируются **в порядке их объявления в классе**, а не в порядке записи в списке конструктора.

```cpp
class Interval {
    const int left_;
    const int right_;

public:
    explicit Interval(int left)
        : left_(left), right_(left_ + 10) {}
};
```

Здесь `right_` вычисляется по уже инициализированному `left_`. Не стоит записывать список инициализации в другом порядке: это затрудняет чтение и может скрывать обращение к еще неинициализированному полю.

### 2.4. Влияние на копирование и присваивание

```cpp
#include <type_traits>

struct Record {
    const int id;
    int value;
};

static_assert(std::is_copy_constructible_v<Record>);
static_assert(!std::is_copy_assignable_v<Record>);
static_assert(!std::is_move_assignable_v<Record>);

void example() {
    Record a{1, 10};
    Record b = a; // Новый объект: const-поле можно инициализировать.

    // b = a;    // Ошибка: неявный оператор присваивания удален.
}
```

**Конструктор копирования** создает новый объект и инициализирует его поля. **Оператор присваивания** работает с уже существующим объектом. Неявные/defaulted операторы присваивания не могут присвоить новое значение полю `const int` и поэтому определяются как удаленные.

Пользовательский оператор присваивания написать можно, например изменяя только `value` и сохраняя `id`. Но такая семантика должна быть осмысленной: после `b = a` идентификаторы останутся разными.

Практический вывод: если требуется лишь запретить пользователю менять поле напрямую, часто достаточно сделать обычное поле `private` и предоставить только метод чтения. Это сохраняет больше возможностей для присваивания объектов.

## 3. Константные методы и указатель this

### 3.1. Что означает const после скобок

```cpp
class Counter {
    int value_ = 0;

public:
    int value() const {
        return value_;
    }

    void increment() {
        ++value_;
    }
};
```

Для обычных нестатических методов класса `Counter`:

- внутри неконстантного метода выражение `this` имеет тип `Counter*`;
- внутри метода с завершающим `const` — тип `const Counter*`.

Поэтому через `this` нельзя изменить обычное поле в константном методе:

```cpp
// int value() const {
//     ++value_; // Ошибка: изменение поля через const-доступ к объекту.
//     return value_;
// }
```

Выражение `this` само по себе не является переменной, которой можно присвоить другой адрес. Объяснение через `Counter* const` иногда используют как аналогию с неявным параметром, но точный тип выражения `this` — `Counter*` или `const Counter*` в рассматриваемых случаях.

### 3.2. Какие методы доступны

```cpp
Counter a;
const Counter b;

a.increment(); // Можно.
a.value();     // Можно.
b.value();     // Можно.
// b.increment(); // Нельзя.
```

| Доступ к объекту | Метод без завершающего `const` | Метод с завершающим `const` |
| --- | --- | --- |
| `Counter&` | Доступен | Доступен |
| `const Counter&` | Недоступен | Доступен |

Ограничение определяется типом доступа. Через `const Counter&` нельзя вызвать неконстантный метод, даже если ссылка указывает на изначально неконстантный объект.

```cpp
void print_value(const Counter& counter) {
    int x = counter.value();
    (void)x;
    // counter.increment(); // Ошибка.
}
```

### 3.3. Перегрузка по константности

Нестатические методы могут отличаться завершающим `const`:

```cpp
#include <string>

class User {
    std::string name_ = "guest";

public:
    std::string& name() {
        return name_;
    }

    const std::string& name() const {
        return name_;
    }
};
```

```cpp
User user;
user.name() = "Vasiliy"; // Выбрана неконстантная перегрузка.

const User& view = user;
const std::string& text = view.name(); // Выбрана const-перегрузка.
// view.name() = "Other";             // Ошибка.
```

Возвращаемая ссылка должна учитывать константность объекта. Нельзя напрямую вернуть `std::string&` на обычное поле из `const`-метода: это позволило бы обходить ограничение.

**Ссылка не продлевает автоматически жизнь объекта, из которого она получена.** Если объект уничтожен, сохраненная ссылка на его поле становится висячей. Для маленьких значений вроде `int` обычно проще возвращать значение.

### 3.4. const в объявлении и определении

```cpp
class Value {
    int value_ = 0;

public:
    int get() const;
};

int Value::get() const {
    return value_;
}
```

Завершающий `const` должен присутствовать и в объявлении, и в соответствующем определении. Без него получится попытка определить другую функцию.

## 4. Границы константности и mutable

### 4.1. const-метод не обязан быть без побочных эффектов

`const` ограничивает изменение объекта через константный путь доступа. Он не означает ни «функция ничего не меняет в программе», ни «при одинаковых аргументах всегда получается одинаковый результат».

Константный метод может, например:

- менять статические переменные;
- менять внешние переменные;
- изменять объект, доступный через указатель или ссылку, если его тип допускает изменение;
- менять поля, объявленные `mutable`;
- выполнять ввод-вывод.

### 4.2. Константность указателя и объекта по адресу

```cpp
class View {
    int* ptr_;

public:
    explicit View(int& value) : ptr_(&value) {}

    void set(int value) const {
        *ptr_ = value; // Разрешено: меняется внешний int.
        // ptr_ = nullptr; // Нельзя менять само поле ptr_.
    }
};

void example() {
    int value = 1;
    const View view(value);
    view.set(7); // value теперь равен 7.
}
```

Константность здесь **поверхностная**: она не распространяется автоматически на объект, на который указывает поле.

Полезно различать объявления:

| Тип | Можно изменить адрес в переменной? | Можно изменить `int` через указатель? |
| --- | --- | --- |
| `int*` | Да | Да |
| `const int*` | Да | Нет |
| `int* const` | Нет | Да |
| `const int* const` | Нет | Нет |

Если интерфейс должен предоставлять только чтение внешних данных, подходит указатель `const int*` или ссылка `const int&`.

### 4.3. Для чего нужен mutable

`mutable` разрешает менять нестатическое поле даже у константного объекта. Обычно это нужно для служебного состояния, изменение которого не меняет логическое значение объекта.

```cpp
#include <string>
#include <utility>

class Text {
    std::string text_;
    mutable std::size_t reads_ = 0;

public:
    explicit Text(std::string text) : text_(std::move(text)) {}

    std::size_t size() const {
        ++reads_;
        return text_.size();
    }

    std::size_t reads() const {
        return reads_;
    }
};
```

Другие применения — кеш вычисления и мьютекс для синхронизации константных операций чтения.

**Ограничения:** `mutable` нельзя применять к статическому полю, полю ссылочного типа или полю с константностью верхнего уровня, например `mutable const int x`.

`mutable` не делает доступ потокобезопасным: два одновременных вызова `size()` в этом примере изменяют один и тот же счетчик и требуют синхронизации.

### 4.4. Почему const_cast не исправляет плохой интерфейс

```cpp
const int x = 10;
// const_cast<int&>(x) = 20; // Неопределенное поведение.
```

Само снятие `const` допустимо не во всех контекстах использования, а запись в объект, который изначально был объявлен константным, приводит к неопределенному поведению.

Если объект изначально неконстантный, изменение через корректно полученный неконстантный доступ может быть допустимо. Однако регулярно снимать `const` внутри метода вместо правильной организации полей и перегрузок — плохая основа интерфейса.

## 5. Статические поля класса

### 5.1. Одно общее состояние

**Статическое поле** не является подобъектом каждого экземпляра. Для обычного статического поля существует одна общая переменная, связанная с классом, даже если экземпляры этого класса еще не созданы.

```cpp
class Settings {
public:
    inline static int timeout = 30; // C++17.
};

void example() {
    Settings a;
    Settings b;

    a.timeout = 60;
    // b.timeout и Settings::timeout теперь тоже обозначают значение 60.
}
```

Предпочтительная запись — `Settings::timeout`: она явно показывает, что значение общее.

Статическое поле не добавляет отдельную копию своих данных в каждый экземпляр. При этом точный `sizeof` класса зависит и от выравнивания, других полей, базовых классов и прочих особенностей типа; размер пустого класса также не равен нулю.

### 5.2. Объявление внутри класса, определение снаружи

Классический вариант, работающий и до C++17:

```cpp
// Settings.hpp
class Settings {
public:
    static int timeout; // Объявление.
};
```

```cpp
// Settings.cpp
// #include "Settings.hpp"

int Settings::timeout = 30; // Определение и инициализация.
```

**Объявление** сообщает о существовании члена. **Определение** предоставляет саму переменную.

Для обычного не-`inline` статического поля, используемого с необходимостью существования объекта в программе, требуется определение. В определении за пределами класса ключевое слово `static` не повторяют.

### 5.3. inline static с C++17

```cpp
#include <string>

class Settings {
public:
    inline static int timeout = 30;
    inline static std::string application = "Lecture app";
};
```

Такое объявление внутри класса уже является определением. Его можно поместить в обычный заголовочный файл, включаемый в несколько единиц трансляции, соблюдая правила ODR: определения должны соответствовать друг другу, а не задавать разные значения или разное поведение в разных `.cpp`.

В обычной программе с одним таким классом из общего заголовка это **одна переменная**, а не отдельная копия на каждый `.cpp`.

`inline` у переменной регулирует допустимость определений в нескольких единицах трансляции. Это не обещание ускорения доступа.

### 5.4. Статическое поле нельзя инициализировать конструктором объекта

```cpp
class Example {
    inline static int shared_ = 0;

public:
    // Example() : shared_(1) {} // Ошибка: shared_ не поле экземпляра.

    Example() {
        shared_ = 1; // Присваивание общей переменной, технически допустимо.
    }
};
```

При каждом создании объекта такой конструктор будет заново присваивать общей переменной значение `1`. Обычно это не то поведение, которое нужно для настройки или счетчика.

## 6. Статические методы

### 6.1. Вызов без экземпляра

```cpp
class Math {
public:
    static int square(int x) {
        return x * x;
    }
};

int result = Math::square(7); // 49.
```

У статического метода нет неявно переданного объекта класса и нет указателя `this`.

Его выбирают, когда операция относится к смыслу класса, но для выполнения не требуется конкретный экземпляр: фабричный метод, проверка входных данных, работа с общими настройками.

### 6.2. Доступ к членам класса

```cpp
class Item {
    int value_ = 0;
    inline static int shared_ = 0;

public:
    static void update(Item& item) {
        ++shared_;      // Есть доступ к статическому полю.
        ++item.value_;  // Есть явно указанный объект.

        // ++value_;        // Ошибка: для какого экземпляра?
        // ++this->value_;  // Ошибка: this отсутствует.
    }
};
```

Статический метод имеет права доступа члена класса: он может обращаться к `private`-полям явно переданного объекта своего класса. Поэтому утверждение «статический метод может работать только со статическими полями» неточно. **Без объекта** он не может обращаться к нестатическим полям и вызывать нестатические методы; **с явно указанным объектом** — может.

### 6.3. Определение вне класса

```cpp
class Math {
public:
    static int cube(int x);
};

int Math::cube(int x) {
    return x * x * x;
}
```

`static` пишут в объявлении внутри класса. В определении снаружи его не повторяют.

### 6.4. Вызов через объект

```cpp
Math math;
int a = math.cube(3); // Допустимо.
int b = Math::cube(3); // Явно показывает статический характер.
```

Даже вызов через объект не передает статическому методу `this`. Однако выражение слева от точки вычисляется: если написать `make_object().cube(3)`, функция `make_object()` будет вызвана. Поэтому такая запись может иметь собственные побочные эффекты.

Статические методы нельзя объявлять `virtual`: для них нет выбора реализации по динамическому типу объекта. Они также не могут иметь завершающие квалификаторы `const`, `volatile`, `&` или `&&`.

## 7. Почему статический метод не бывает const

### 7.1. Неверная комбинация

```cpp
class Example {
public:
    // static int get() const; // Ошибка языка.
};
```

Завершающий `const` определяет константность неявного объекта нестатического метода. Статический метод не имеет такого объекта, поэтому квалифицировать его таким способом нельзя. Этот запрет прямо сформулирован в правилах [статических методов C++](https://eel.is/c++draft/class.static.mfct).

Это не означает, что статическая функция обязана что-либо изменять. Она может только читать данные и выполнять вычисления — просто завершающий `const` не является способом выразить такое свойство.

### 7.2. Вызов через константный объект

```cpp
class Service {
    inline static int calls_ = 0;

public:
    static void call() {
        ++calls_;
    }

    static int calls() {
        return calls_;
    }
};

void example() {
    const Service service;
    service.call(); // Допустимо; меняется общая переменная.
    Service::call(); // Также допустимо и понятнее.
}
```

Константность `service` ограничивает этот экземпляр. Статическая переменная `calls_` не является его подобъектом.

### 7.3. const у возвращаемого типа — другое свойство

```cpp
#include <string>

class Registry {
    inline static std::string title_ = "Main";

public:
    static const std::string& title() {
        return title_;
    }
};
```

Здесь `const` относится к строке, доступной через возвращаемую ссылку. Через результат `Registry::title()` строку менять нельзя. При этом сам метод не стал константным, а поле `title_` остается изменяемым для кода с подходящим доступом.

Для скалярного результата `static const int value()` возвращаемый верхнеуровневый `const` почти не дает полезной защиты: вызывающая сторона получает свое значение. Обычно пишут `static int value()`.

### 7.4. Как выразить реальное намерение

| Требование | Подход |
| --- | --- |
| Читать состояние конкретного объекта | Нестатический метод `f() const` |
| Выполнять операцию без объекта | Статический метод `static f()` |
| Запретить менять общую переменную | Поле `static const` или `static constexpr` |
| Предоставить только чтение результата | Возврат значения, `const T&` или `const T*` |
| Разрешить вычисление в константном выражении | Функция `constexpr` |
| Требовать вычисление при компиляции в обычном вызове | Функция `consteval`, C++20 |

Стандартного универсального квалификатора «эта функция не имеет побочных эффектов» у обычных функций C++ нет. Ни `const` у нестатического метода, ни `constexpr` сами по себе не дают такой общей гарантии.

## 8. Константные статические поля и ODR

### 8.1. static const: общий неизменяемый объект

```cpp
class Limits {
public:
    static const int max_users = 100;
};
```

Для не-`inline` статического `const`-поля целочисленного или перечислимого типа допускается инициализатор внутри класса, если он удовлетворяет требованиям константного выражения. Это специальное правило, которое не распространяется автоматически на любой тип.

```cpp
class Geometry {
public:
    // static const double pi = 3.141592653589793; // Не стандартный вариант.
    static const double pi;
};

const double Geometry::pi = 3.141592653589793;
```

С C++17 для определения общей константы в заголовке можно использовать `inline static const`; если требуется константное выражение и тип подходит — `static constexpr`.

### 8.2. Что означает ODR

**ODR — One Definition Rule**, правило одного определения. Оно задает требования к объявлениям и определениям сущностей в программе.

Для обычной не-`inline` статической переменной, которая odr-используется, необходимо одно определение в программе. Для `inline`-переменных разрешены согласованные определения в нескольких единицах трансляции.

**Odr-use** — формальный термин языка. В рассматриваемых примерах практический признак такой: требуется ли существование самой переменной как объекта, например чтобы получить ее адрес или привязать к ней ссылку?

Это полезная ориентировка, а не полное формальное определение odr-use.

### 8.3. Значение можно подставить, но адресу нужен объект

```cpp
class Limits {
public:
    static const int size = 16;
};

int buffer[Limits::size]; // Используется константное значение.
int n = Limits::size;     // Чтение значения: отдельное определение не нужно.

const int* p = &Limits::size; // Нужен сам объект: odr-use.
const int& r = Limits::size;  // Также odr-use.
```

Для двух последних случаев добавляют определение в одном `.cpp`:

```cpp
const int Limits::size; // Без повторного инициализатора.
```

Даже в C++17 и новее обычное объявление `static const int size = 16;` **не становится `inline` автоматически**. Если нужен адрес, правило об отдельном определении сохраняется.

### 8.4. Неожиданное odr-use через std::min

```cpp
#include <algorithm>

class Bounds {
public:
    static const int limit = 100;
};

const int Bounds::limit; // Требуется для использования ниже.

int clamp_value(int x) {
    return std::min(x, Bounds::limit);
}
```

Двухаргументный `std::min` принимает аргументы по `const T&`. Поэтому передача `Bounds::limit` связывает с полем ссылку и требует определения. Оптимизация конкретной сборки может скрыть отсутствие определения, но полагаться на это нельзя.

Для C++17 удобнее:

```cpp
class BoundsModern {
public:
    static constexpr int limit = 100;
};
```

### 8.5. Правила по версиям языка

| Объявление внутри класса | C++11/C++14 | C++17 и новее |
| --- | --- | --- |
| `static int n;` | Объявление; при odr-use нужно определение снаружи | То же |
| `static const int n = 10;` | При odr-use нужно определение снаружи без инициализатора | То же: автоматически `inline` не становится |
| `static constexpr int n = 10;` | При odr-use нужно определение снаружи без инициализатора | Неявно `inline`; отдельное определение не нужно |
| `inline static int n = 10;` | Не поддерживается | Определение внутри класса |
| `inline static const int n = 10;` | Не поддерживается | Определение внутри класса |

До C++17 для odr-используемого `constexpr`-поля писали:

```cpp
class OldLimits {
public:
    static constexpr int size = 16;
};

constexpr int OldLimits::size; // В одном .cpp, без инициализатора.
```

С C++17 это внешнее повторное объявление избыточно и относится к устаревающей форме записи.

## 9. constexpr, consteval и constinit

### 9.1. const не всегда означает константу времени компиляции

```cpp
int read_limit(); // Реализация получает значение во время выполнения.

class RuntimeLimits {
public:
    static const int limit;
};

const int RuntimeLimits::limit = read_limit();
```

После инициализации `limit` изменять нельзя, но значение не обязано быть известно компилятору как константное выражение.

Некоторые `const`-переменные целочисленного или перечислимого типа с подходящей инициализацией пригодны для константных выражений. Поэтому неверны оба упрощения: «любой `const` известен при компиляции» и «никакой `const` не подходит для вычислений при компиляции».

### 9.2. static constexpr-поля

```cpp
#include <array>
#include <string_view>

class Protocol {
public:
    static constexpr int version = 2;
    static constexpr double scale = 0.5;
    static constexpr std::string_view name = "LectureProtocol";
    static constexpr std::array<int, 3> supported{1, 2, 3};
};

static_assert(Protocol::version == 2);
static_assert(Protocol::supported[1] == 2);
```

Пример рассчитан на C++17. У `constexpr`-объекта есть константность и требования к инициализации, позволяющие использовать его в предусмотренных языком константных выражениях. Тип должен удовлетворять требованиям для такого объявления.

С C++17 статическое `constexpr`-поле неявно является `inline`, поэтому удобно для констант в заголовках.

`std::string_view` не владеет символами. В примере он ссылается на строковый литерал с подходящим временем жизни; ссылаться на уничтоженную временную строку было бы ошибкой.

### 9.3. static constexpr-метод

```cpp
class MathTools {
public:
    static constexpr int square(int x) noexcept {
        return x * x;
    }
};

static_assert(MathTools::square(5) == 25);
constexpr int compile_time = MathTools::square(6);

int runtime_square(int input) {
    return MathTools::square(input);
}
```

Здесь совместимы три независимых свойства:

- `static`: не нужен объект класса;
- `constexpr`: вызов может участвовать в константном выражении при выполнении соответствующих условий;
- `noexcept`: функция объявлена не допускающей выхода исключения наружу; это не означает отсутствие побочных эффектов.

`constexpr`-функция может вызываться и во время выполнения. Конкретный вызов обязан вычисляться как константное выражение, если этого требует контекст, например инициализация `constexpr`-переменной или условие `static_assert`.

В примере предполагается, что умножение не вызывает переполнение знакового `int`. При вычислении допустимого константного выражения неопределенное поведение недопустимо.

### 9.4. constexpr не равно const у метода

Начиная с C++14, нестатический `constexpr`-метод не становится константным автоматически:

```cpp
class Number {
    int value_;

public:
    constexpr explicit Number(int value) : value_(value) {}

    constexpr int get() const {
        return value_;
    }
};

constexpr Number number(7);
static_assert(number.get() == 7);
```

Завершающий `const` здесь указан отдельно и нужен для вызова на константном объекте `number`.

В C++11 у нестатических `constexpr`-методов действовало специальное правило неявной константности. Для современного кода следует явно разделять эти свойства.

`constexpr` также не означает абсолютную чистоту функции: например, допустимая `constexpr`-функция может изменять объект, переданный по неконстантной ссылке. Условия пригодности конкретного вызова для константного выражения проверяются отдельно.

### 9.5. consteval: обязательное вычисление при компиляции

```cpp
class BuildTime {
public:
    static consteval int square(int x) {
        return x * x;
    }
};

constexpr int value = BuildTime::square(8); // 64, C++20.

int use_input(int input) {
    // return BuildTime::square(input); // Ошибка: input неизвестен при компиляции.
    return input;
}
```

Для обычного вызова `consteval`-функции требуется константное вычисление. В языке есть дополнительные правила контекста непосредственных функций; в типичном прикладном коде различие простое: `constexpr` допускает вычисление при компиляции, `consteval` требует его.

### 9.6. constinit: контроль инициализации, а не неизменяемость

```cpp
class Startup {
public:
    inline static constinit int retries = 3; // C++20.
};

void increase_retries() {
    ++Startup::retries; // Разрешено.
}
```

`constinit` применяется к переменным со статической или потоковой длительностью хранения и запрещает динамическую инициализацию соответствующей переменной. При этом он не делает переменную константной и сам по себе не превращает ее значение в константное выражение для последующих обращений.

| Спецификатор | Основное назначение |
| --- | --- |
| `const` | Ограничение изменения объекта или доступа через него |
| `constexpr` у объекта | Константность и требования для константной инициализации |
| `constexpr` у функции | Возможность константного вычисления подходящих вызовов |
| `consteval` у функции | Непосредственная функция, обычные вызовы вычисляются при компиляции |
| `constinit` у переменной | Исключение динамической инициализации; изменение потом может быть разрешено |

## 10. Время жизни, инициализация и потоки

### 10.1. Статическое поле живет независимо от экземпляров

Обычное статическое поле имеет статическую длительность хранения. Его существование не привязано к времени жизни одного экземпляра класса. Поле, объявленное также `thread_local`, имеет потоковую длительность хранения.

```cpp
class Cache {
public:
    inline static int hits = 0;
};

void use_cache() {
    Cache::hits = 1; // Ни один экземпляр Cache не нужен.
}
```

Числовые переменные со статической длительностью хранения без явного инициализатора получают нулевую инициализацию. Это отличается от обычного неинициализированного локального `int`.

### 10.2. Опасность порядка динамической инициализации

Статические поля могут инициализироваться вызовами функций или конструкторами сложных объектов. Если инициализатор одного такого объекта обращается к другому объекту из другого `.cpp`, нужный порядок не всегда гарантирован.

```cpp
// В одном .cpp:
// std::string Application::name = make_name();

// В другом .cpp:
// std::string Logger::prefix = Application::name + ": ";
```

Если между инициализациями не установлено требуемое упорядочение, обращение может произойти до завершения конструирования строки. Это известная проблема порядка статической инициализации.

Вариант организации — создавать объект при первом обращении:

```cpp
#include <string>

class Application {
public:
    static const std::string& name() {
        static const std::string value = "Lecture app";
        return value;
    }
};
```

Локальная статическая переменная с динамической инициализацией инициализируется при первом прохождении управления через ее объявление. Начиная с C++11 параллельные обращения защищены от одновременного выполнения этой инициализации. Если инициализация завершилась исключением, следующее обращение может повторить попытку.

Это решает вопрос момента создания, но не все вопросы времени жизни: обращения из деструкторов других статических объектов также требуют учитывать порядок уничтожения.

### 10.3. static не обеспечивает потокобезопасность

```cpp
class Statistics {
public:
    inline static int requests = 0;

    static void add_request() {
        ++requests;
    }
};
```

Если два потока вызывают `add_request()` без синхронизации, возникает гонка данных. Операция `++` над обычным `int` не является автоматически атомарной. Для C++ гонка данных означает неопределенное поведение.

Для независимого счетчика можно использовать атомарную переменную:

```cpp
#include <atomic>

class SafeStatistics {
    inline static std::atomic<int> requests_{0};

public:
    static void add_request() noexcept {
        requests_.fetch_add(1, std::memory_order_relaxed);
    }

    static int requests() noexcept {
        return requests_.load(std::memory_order_relaxed);
    }
};
```

`memory_order_relaxed` здесь подходит, если счетчик нужен только как отдельное числовое значение и не должен обеспечивать видимость каких-либо других данных. Более сложные инварианты могут требовать мьютекса или другого протокола синхронизации.

Потокобезопасная **инициализация** локальной статической переменной не означает потокобезопасность всех последующих **операций** с ней.

### 10.4. thread_local: отдельное значение в каждом потоке

```cpp
class ThreadStatistics {
public:
    inline static thread_local int requests = 0;
};
```

Такой счетчик общий для объектов класса **в пределах одного потока**, но у разных потоков существуют отдельные значения. Это не единый суммарный счетчик всей программы.

## 11. Наследование, шаблоны и указатели на функции

### 11.1. Наследование не создает новую копию статического поля

```cpp
struct Base {
    inline static int value = 0;
};

struct Derived : Base {};

void example() {
    Derived::value = 5;
    // Base::value тоже равен 5: это одно и то же поле.
}
```

Если производный класс объявляет собственный статический член с таким же именем, он скрывает имя базового члена, а не переопределяет его виртуально:

```cpp
struct AnotherDerived : Base {
    inline static int value = 10; // Другая переменная.
};
```

Статические методы также могут скрываться по имени, но не участвуют в виртуальной диспетчеризации.

### 11.2. У каждой специализации шаблона свое статическое поле

```cpp
template <typename T>
struct TypeStatistics {
    inline static int count = 0;
};

void example() {
    ++TypeStatistics<int>::count;
    ++TypeStatistics<int>::count;
    ++TypeStatistics<double>::count;

    // Для int: 2. Для double: 1.
}
```

`TypeStatistics<int>` и `TypeStatistics<double>` — разные классы, поэтому их статические поля различаются. При этом все объекты одной и той же специализации разделяют соответствующее общее поле.

### 11.3. Адрес статического метода

```cpp
class Calculator {
public:
    static int twice(int x) {
        return 2 * x;
    }

    int triple(int x) const {
        return 3 * x;
    }
};

void example() {
    int (*function)(int) = &Calculator::twice;
    int a = function(5); // 10, объект не нужен.

    int (Calculator::*method)(int) const = &Calculator::triple;
    Calculator calculator;
    int b = (calculator.*method)(5); // 15, объект нужен.

    (void)a;
    (void)b;
}
```

Указатель на статический метод — обычный указатель на функцию соответствующего типа. Указатель на нестатический метод имеет специальный тип указателя на член и применяется к объекту.

### 11.4. Другие значения слова static

| Место объявления | Значение `static` |
| --- | --- |
| Поле класса | Общее состояние класса, а не поле каждого объекта |
| Метод класса | Нет неявного объекта и `this` |
| Локальная переменная функции | Статическая длительность хранения, сохранение состояния между вызовами |
| Свободная функция или переменная в пространстве имен | Внутреннее связывание имени; для переменной также статическая длительность хранения |

Эти значения связаны с одним ключевым словом, но не взаимозаменяемы. Например, `static` у свободной функции и `static` у метода класса решают разные задачи.

## 12. Цельный пример класса

Пример для C++17 объединяет постоянный идентификатор экземпляра, изменяемое имя, общую константу, статическую проверку и фабричный метод.

```cpp
#include <cassert>
#include <cstddef>
#include <stdexcept>
#include <string>
#include <string_view>
#include <utility>

class Profile {
    const int id_;
    std::string name_;

public:
    static constexpr std::size_t max_name_length = 32;
    static constexpr std::string_view default_name = "guest";

    static bool valid_name(std::string_view name) noexcept {
        return !name.empty() && name.size() <= max_name_length;
    }

    Profile(int id, std::string name)
        : id_(id), name_(std::move(name)) {
        if (!valid_name(name_)) {
            throw std::invalid_argument("Invalid name");
        }
    }

    static Profile guest(int id) {
        return Profile(id, std::string(default_name));
    }

    int id() const noexcept {
        return id_;
    }

    const std::string& name() const noexcept {
        return name_;
    }

    void rename(std::string name) {
        if (!valid_name(name)) {
            throw std::invalid_argument("Invalid name");
        }
        name_ = std::move(name);
    }
};

int main() {
    Profile first(101, "Vasiliy");
    const Profile second = Profile::guest(202);

    first.rename("Developer");

    assert(first.id() == 101);
    assert(first.name() == "Developer");
    assert(second.id() == 202);
    assert(second.name() == "guest");
    assert(Profile::valid_name("User"));

    // second.rename("Other"); // Нельзя: second константный.
    // first = second;          // Неявный operator= удален из-за const int id_.
}
```

Разбор решений:

1. `id_` принадлежит конкретному объекту и инициализируется в конструкторе.
2. `name_` также индивидуально, но может изменяться через проверяющий метод.
3. `max_name_length` и `default_name` общие и не требуют отдельных определений в C++17.
4. `valid_name()` не нужен экземпляр, поэтому метод статический. Завершающий `const` ему не требуется и не разрешен.
5. `guest()` — статический фабричный метод: создает и возвращает новый объект.
6. `id()` и `name()` читают состояние экземпляра, поэтому объявлены `const`.
7. `rename()` меняет логическое состояние объекта, поэтому не является константным методом.

В этом примере длина `std::string` измеряется в элементах `char`. Для строки UTF-8 это количество байтов, а не число видимых пользователю символов.

## 13. Типичные ошибки и выбор объявления

### 13.1. Ошибки и исправления

| Ошибка или заблуждение | Причина | Исправление |
| --- | --- | --- |
| `static int get() const;` | Нет неявного объекта, константность которого можно квалифицировать | `static int get();` или нестатический `int get() const;` |
| Присвоить `const`-полю значение в теле конструктора | Это уже существующее поле | Инициализировать в списке конструктора или в объявлении |
| Объявить `static int x;` и забыть определение при odr-use | Одного объявления недостаточно | Определить в одном `.cpp` или использовать `inline static` с C++17 |
| Положить обычное `int Class::x = 0;` в общий заголовок | Несколько определений при включении из разных `.cpp` | Перенести определение в `.cpp` либо сделать переменную `inline` |
| Считать `static const int n = 10` автоматически `inline` | Для обычного `static const` такого правила нет | При odr-use добавить определение или выбрать `static constexpr` с C++17 |
| Обращаться к `value_` из статического метода без объекта | Неизвестно, чей экземпляр используется | Передать объект явно либо сделать метод нестатическим |
| Ожидать, что `const`-метод вообще ничего не меняет | `const` не запрещает все побочные эффекты | Проверять работу с внешними данными, `mutable` и статическим состоянием |
| Считать `constexpr`-функцию всегда выполняемой при компиляции | Это зависит от контекста вызова | Использовать обязательный константный контекст или `consteval` |
| Считать `inline` или `static` защитой от гонок | Они не синхронизируют доступ | Использовать атомарные операции или мьютекс |
| Ожидать, что `constinit` запрещает изменение | Он контролирует инициализацию | Для неизменяемости использовать `const`/`constexpr` |

### 13.2. Практический выбор

- **Постоянное значение конкретного объекта:** `const T field`, если действительно нужна такая модель и подходят ограничения присваивания.
- **Закрытое поле с чтением снаружи:** `private`-поле и `const`-метод доступа; само поле не обязательно объявлять `const`.
- **Общая изменяемая настройка:** `inline static T field = ...` с C++17; доступ и синхронизацию проектируют отдельно.
- **Общая константа времени компиляции:** `static constexpr T field = ...` с подходящим типом и инициализатором.
- **Общая неизменяемая величина времени выполнения:** `inline static const T field = ...` с C++17 либо определение в `.cpp`.
- **Чтение состояния экземпляра:** нестатический метод с завершающим `const`.
- **Операция без состояния экземпляра:** статический метод или свободная функция, в зависимости от смысла интерфейса.

## 14. Вопросы для самопроверки

### Задание 1. Найти ошибки

```cpp
class Test {
    int x_ = 0;
    const int id_;
    inline static int shared_ = 0;

public:
    explicit Test(int id) : id_(id) {}

    // static int first() const { return shared_; }
    // static int second() { return x_; }

    int third() const {
        ++shared_;
        return x_;
    }
};
```

**Ответ:**

- `first()` некорректен из-за `const` после списка параметров статического метода.
- `second()` некорректен: для `x_` не указан объект.
- `third()` корректен в однопоточном контексте: статическое поле можно изменить из `const`-метода, а `x_` только читается.

### Задание 2. Нужны ли отдельные определения в C++17?

```cpp
struct Values {
    static const int a = 10;
    static constexpr int b = 20;
    inline static const int c = 30;
};

const int* pa = &Values::a;
const int* pb = &Values::b;
const int* pc = &Values::c;
```

**Ответ:** для `a` нужно определение `const int Values::a;` в одном `.cpp`. Для `b` и `c` отдельные определения не требуются: в C++17 обе переменные являются `inline`.

### Задание 3. Какая перегрузка вызывается?

```cpp
struct Box {
    int get() { return 1; }
    int get() const { return 2; }
};

Box box;
const Box& view = box;

int a = box.get();
int b = view.get();
```

**Ответ:** `a == 1`, `b == 2`. Для неконстантного объекта предпочтительна неконстантная перегрузка, а через `const Box&` доступна константная.

### Задание 4. Что произойдет при присваивании?

```cpp
struct Entity {
    const int id;
    int score;
};

Entity first{1, 10};
Entity second = first;
// second = first;
```

**Ответ:** создание `second` копированием допустимо. Закомментированное присваивание не компилируется: неявный оператор присваивания удален из-за поля `const int id`.

### Задание 5. Можно ли вызвать статический метод через const-объект?

```cpp
struct Utility {
    static int answer() { return 42; }
};

const Utility utility;
int value = utility.answer();
```

**Ответ:** да, `value == 42`. У статического метода нет `this`, и константность `utility` не влияет на его доступность. Более ясная запись — `Utility::answer()`.

## Главное

1. **`static` и `const` описывают разные свойства.** Первое отделяет член от состояния отдельного экземпляра, второе ограничивает изменение или доступ.
2. **Константное поле инициализируют при создании объекта.** Присвоить ему значение в теле конструктора нельзя; такое поле может ограничить присваивание всего класса.
3. **`const` после скобок относится к неявному объекту метода.** В обычном `const`-методе `this` имеет тип указателя на константный объект класса.
4. **Статического метода с завершающим `const` в C++ нет.** У него отсутствует неявный объект и указатель `this`.
5. **Статическая переменная общая для класса.** Константность отдельного экземпляра не запрещает изменять общую изменяемую переменную.
6. **`const`-метод не гарантирует отсутствия побочных эффектов.** Возможны изменения статических и внешних данных, объектов по указателям и полей `mutable`.
7. **Нужно различать объявление и определение.** Обычному `static const int` при odr-use требуется определение снаружи; с C++17 `static constexpr` неявно является `inline`.
8. **`constexpr`, `consteval` и `constinit` не взаимозаменяемы.** Они отвечают за возможность константных вычислений, обязательность таких вызовов и контроль статической инициализации соответственно.
9. **Общее статическое состояние требует продуманной синхронизации.** Ни `static`, ни `inline`, ни `const` у метода сами по себе не защищают от гонок данных.
