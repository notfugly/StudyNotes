# Шаблонное метапрограммирование: CRTP, шаблоны выражений, SFINAE

**Предмет:** C++. **Дата занятия:** 23.10.2026.

Основные примеры используют **C++17**. Примеры с `concept`, `requires` и `std::integral` относятся к **C++20** и отмечены отдельно. Полные программы можно компилировать независимо; короткие фрагменты поясняют отдельные конструкции.

## Основы шаблонного метапрограммирования

### Шаблон, специализация и инстанцирование

**Шаблон** задаёт семейство классов, функций или других шаблонных сущностей. Параметрами могут быть типы, допустимые значения времени компиляции и другие шаблоны.

```cpp
template<class T>
T twice(T value) {
    return value + value;
}

int a = twice(7);        // T = int
double b = twice(2.5);   // T = double
```

`twice<int>` и `twice<double>` — разные **специализации** шаблона функции. **Инстанцирование** — процесс, при котором компилятор формирует необходимые объявления и определения из шаблона для конкретных аргументов.

Не следует понимать шаблон как простую текстовую подстановку: действуют правила типов, поиска имён, вывода аргументов, разрешения перегрузок и проверки ограничений.

**Шаблонное метапрограммирование** использует шаблоны для вычисления свойств, выбора типов и реализаций, проверки допустимости операций и построения специализированного кода при компиляции.

### Вычисление при компиляции и выполнение программы

Нужно различать два действия:

1. Компилятор определяет, **какие типы и функции** участвуют в программе.
2. Сгенерированная программа выполняет действия над конкретными данными.

Вызов `twice(x)` не обязан вычисляться при компиляции. Аналогично, в CRTP заранее выбирается реализация метода, но обработка данных обычно происходит во время выполнения.

В шаблонах выражений структура операции представлена типами, а элементы векторов могут вычисляться обычным циклом при выполнении программы. Слово «метапрограммирование» не означает, что все значения известны компилятору.

### Признаки типов и метафункции

**Признак типа, type trait** — шаблон, сообщающий свойство типа. Стандартные признаки находятся в `<type_traits>`.

```cpp
#include <type_traits>

static_assert(std::is_integral_v<int>);
static_assert(!std::is_integral_v<double>);
static_assert(std::is_same_v<std::remove_reference_t<int&>, int>);
```

- `std::is_integral<T>::value` — логическое значение: является ли `T` целочисленным типом.
- `std::is_integral_v<T>` — сокращение для этого значения, доступное с C++17.
- `std::remove_reference<T>::type` — тип `T` без ссылки.
- `std::remove_reference_t<T>` — сокращение для этого типа, доступное с C++14.

Метафункция может возвращать не значение, а **тип** через вложенное имя `type`.

### Зависимые имена: typename и this

В конструкции

```cpp
template<class T>
using element_t = typename T::value_type;
```

`T::value_type` зависит от параметра шаблона. В таком объявлении `typename` сообщает, что зависимое имя обозначает тип.

При обращении к члену зависимого базового класса часто требуется `this->`:

```cpp
template<class T>
struct Parent {
    void reset() {}
};

template<class T>
struct Child : Parent<T> {
    void clear() {
        this->reset();
    }
};
```

Зависимые имена проверяются с учётом конкретных аргументов шаблона. Однако независимые синтаксические ошибки и многие ошибки независимых имён обнаруживаются уже при разборе определения шаблона.

## CRTP: идея и механизм

### Определение

**CRTP, Curiously Recurring Template Pattern** — приём, при котором класс наследуется от специализации шаблонного базового класса, передавая в этот шаблон собственный тип:

```cpp
template<class Derived>
struct Base {
    // Общая функциональность для Derived.
};

struct Concrete : Base<Concrete> {
    // Конкретная реализация.
};
```

Базовый шаблон получает информацию о типе наследника и может обращаться к его реализации через `static_cast`.

Название «повторяющийся» связано с появлением имени наследника в аргументе базы. Бесконечной цепочки объектов здесь нет: `Concrete` содержит базовый подобъект `Base<Concrete>`, а сама база не обязана содержать объект `Concrete`.

### Полная программа: статический интерфейс фигур

```cpp
#include <iostream>

template<class Derived>
class Shape {
public:
    double area() const {
        return derived().area_impl();
    }

protected:
    ~Shape() = default;

private:
    const Derived& derived() const {
        return static_cast<const Derived&>(*this);
    }
};

class Circle : public Shape<Circle> {
public:
    explicit Circle(double radius) : radius_(radius) {}

    double area_impl() const {
        constexpr double pi = 3.141592653589793;
        return pi * radius_ * radius_;
    }

private:
    double radius_;
};

class Rectangle : public Shape<Rectangle> {
public:
    Rectangle(double width, double height)
        : width_(width), height_(height) {}

    double area_impl() const {
        return width_ * height_;
    }

private:
    double width_;
    double height_;
};

template<class Derived>
void print_area(const Shape<Derived>& shape) {
    std::cout << shape.area() << '\n';
}

int main() {
    Circle circle(2.0);
    Rectangle rectangle(3.0, 4.0);

    print_area(circle);     // Приблизительно 12.5664.
    print_area(rectangle);  // 12.
}
```

Предполагается, что размеры фигур неотрицательны.

### Как работает вызов

Рассмотрим `circle.area()`:

1. `Circle` наследует метод `area()` от `Shape<Circle>`.
2. В этой специализации `Derived` обозначает `Circle`.
3. Внутри `derived()` выражение `*this` имеет тип `const Shape<Circle>&`.
4. `static_cast<const Circle&>(*this)` получает ссылку на содержащий базовый подобъект объект `Circle`.
5. Вызывается `Circle::area_impl()`.

**Условие корректности приведения:** базовый подобъект действительно должен принадлежать объекту соответствующего производного типа. `static_cast` не выполняет динамическую проверку этого условия.

В данном примере нет виртуального вызова. Компилятор видит конкретную реализацию и может встроить её, но стандарт языка **не гарантирует** встраивание или выигрыш в скорости.

### Почему разрешено передавать ещё не завершённый тип

При разборе

```cpp
class Circle : public Shape<Circle> {
    // ...
};
```

тип `Circle` ещё не завершён. Использовать такой тип в качестве аргумента шаблона само по себе разрешено.

Это работает, пока при формировании базы не требуется информация, которая доступна только после завершения наследника. Определения обычных функций-членов шаблонного класса, как правило, инстанцируются тогда, когда понадобятся. Поэтому зависимый вызов внутри `area()` можно проверить позже.

Следующий подход, напротив, проблематичен:

```cpp
template<class Derived>
struct BadBase {
    using value_type = typename Derived::value_type;
};

struct Item : BadBase<Item> {
    using value_type = int;
};
```

При формировании `BadBase<Item>` компилятору уже нужен `Item::value_type`, хотя тело `Item` ещё не разобрано полностью.

Возможные решения: передать нужный тип отдельным параметром базы, вынести сведения в заранее объявленный traits-класс или отложить обращение до инстанцирования тела метода. Правила отложенного инстанцирования описаны в разделе стандарта [temp.inst](https://eel.is/c++draft/temp.inst).

## Применение и ограничения CRTP

### Добавление общей функциональности

CRTP полезен, когда несколько типов должны получить одинаковый алгоритм, опирающийся на небольшую конкретную операцию.

Например, наследник реализует `step()`, а база предоставляет повторение этой операции:

```cpp
#include <cassert>
#include <cstddef>

template<class Derived>
struct Repeatable {
    void repeat(std::size_t count) {
        auto& self = static_cast<Derived&>(*this);
        for (std::size_t i = 0; i < count; ++i) {
            self.step();
        }
    }
};

struct Counter : Repeatable<Counter> {
    int value = 0;

    void step() {
        ++value;
    }
};

int main() {
    Counter counter;
    counter.repeat(3);
    assert(counter.value == 3);
}
```

Такую базу часто называют **mixin**: она добавляет поведение к классу. Не каждый mixin использует CRTP, но CRTP позволяет mixin-базе обращаться к конкретному наследнику.

Другие применения: реализация производных операторов через базовые операции, общий интерфейс итераторов, возврат ссылки на конкретный тип в цепочках вызовов, основы библиотек выражений.

### Статический и динамический полиморфизм

**Полиморфизм** позволяет работать через общий способ обращения с разными реализациями. При CRTP этот способ часто оформлен шаблонной функцией.

| Свойство | CRTP | Виртуальные функции |
|---|---|---|
| Основа механизма | Шаблонная база с типом наследника | Общая полиморфная база и переопределение |
| Выбор реализации | По статическим типам при компиляции | По динамическому типу объекта |
| Общая база для разных наследников | `Shape<Circle>` и `Shape<Rectangle>` — разные типы | Оба наследника могут иметь одну базу `Shape` |
| Хранение разных реализаций в одном контейнере | Нужен дополнительный механизм, например `std::variant` или стирание типа | Возможно через указатели на общую базу |
| Возможности оптимизации | Конкретная реализация видна через шаблон | Возможна девиртуализация, если компилятор установит реализацию |
| Цена | Больше специализаций и зависимостей от заголовков | Возможные косвенные вызовы и служебные данные объекта |

CRTP сам по себе не создаёт единого нешаблонного типа «любая фигура». Если тип реализации выбирается только во время выполнения, обычно удобнее динамический полиморфизм, `std::variant` для фиксированного набора типов или стирание типа.

### Типичные ошибки

**1. Передача неправильного типа в базу.**

```cpp
struct First : Repeatable<First> {
    void step() {}
};

struct Second : Repeatable<First> {
    // Ошибка проектирования: передан First вместо Second.
};
```

Само наследование может быть принято компилятором. Но вызов у объекта `Second` метода базы, выполняющего приведение к `First&`, нарушает условие корректности приведения.

**2. Отсутствие реализации.** Если наследник не определил `step()`, ошибка обычно возникает при инстанцировании вызывающего её метода. Сам факт наследования не равнозначен немедленной проверке интерфейса.

**3. Рекурсия из-за совпадающих имён.** Если база вызывает через наследника метод с тем же именем, а наследник его не определил, поиск может найти унаследованный метод базы. Тогда вместо диагностики отсутствующей реализации получится рекурсия. Разделение имён `area()` и `area_impl()` делает намерение яснее.

**4. Вызов реализации наследника из конструктора базы.** Наследник ещё не полностью инициализирован; его поля могут быть недоступны для корректного использования. Аналогичная осторожность нужна при разрушении объекта. Вызовы такого рода лучше выполнять после завершения конструирования.

**5. Удаление через базу без подходящего интерфейса разрушения.** CRTP-база не обязана иметь виртуальный деструктор. Удалять наследника через указатель на такую базу нельзя, если не выполнены правила безопасного полиморфного удаления. Защищённый деструктор, как у `Shape`, запрещает обычный внешний `delete` через указатель на базу.

**6. Потеря const-корректности.** Для константного объекта нужен путь к `const Derived&`. Нельзя снимать константность ради вызова изменяющей реализации.

## Шаблоны выражений: идея и вычисление

### Проблема промежуточных результатов

Пусть векторный `operator+` немедленно создаёт и заполняет новый вектор. Тогда

```cpp
result = a + b + c;
```

по правилам группировки означает

```cpp
result = (a + b) + c;
```

При такой реализации сначала вычисляется вектор `a + b`, затем к нему прибавляется `c`. Возникают дополнительные промежуточные данные и проходы по памяти.

Перемещение и устранение копий могут убрать часть копирования объектов, но не обязаны убрать выделение памяти и заполнение промежуточного массива, заложенные в реализацию операций.

### Представление операции объектом

**Шаблоны выражений, expression templates** — техника, при которой операторы строят типизированные объекты, описывающие операции. Полное вычисление откладывается до момента, когда нужен результат.

Вместо готового вектора `a + b` возвращается объект узла суммы. Его логический интерфейс:

```cpp
sum.size();  // Количество элементов.
sum[i];      // Вычисляет left[i] + right[i].
```

Для `(a + b) + c` строятся два узла. Тип внешнего узла содержит информацию о типах внутренних операций и операндов. Конкретное написание типа зависит от реализации хранения ссылок и значений.

Сами объекты узлов существуют во время выполнения: они могут хранить ссылки на реальные массивы. Компилятор знает структуру их типов и может оптимизировать обход.

### Ленивое вычисление и слияние циклов

Для каждого индекса вычисляется

$$
r_i = (a_i + b_i) + c_i, \qquad 0 \le i < n.
$$

Материализация результата сводится к одному циклу:

```cpp
for (std::size_t i = 0; i < n; ++i) {
    result[i] = (a[i] + b[i]) + c[i];
}
```

Это называют **слиянием циклов, loop fusion**. При фиксированном количестве слагаемых асимптотическая сложность остаётся $O(n)$, но могут уменьшиться число выделений памяти, количество промежуточных записей и нагрузка на память.

Для $k$ векторов длины $n$ количество поэлементных сложений составляет $(k-1)n$ и при обычном подходе, и при слиянии. Основная цель — изменить организацию вычисления, а не арифметический результат или само число необходимых сложений.

**Ленивое вычисление** откладывает операцию. **Материализация** создаёт объект, который уже хранит вычисленные значения. Ленивость сама по себе не означает кэширование: повторный доступ к выражению может повторять вычисления.

### Роль CRTP

База `Expr<Derived>` задаёт общий способ получения конкретного выражения. Вектор и узлы операций могут наследоваться от соответствующих специализаций этой базы.

CRTP здесь обеспечивает статический интерфейс, а узлы выражений описывают вычисление. Шаблоны выражений можно реализовать и без CRTP — например, через проверку нужных методов и constraints. Это связанные, но самостоятельные техники.

## Реализация шаблонов выражений

### Как хранить операнды

Простая идея «все операнды хранить по `const&`» опасна. В выражении `(a + b) + c` внутренний узел `a + b` временный. Если внешний узел сохраняет только ссылку на него, после завершения полного выражения ссылка может стать висячей.

Используем следующую политику:

- **lvalue**, то есть в данном примере именованные существующие объекты, сохраняются через `std::reference_wrapper<const T>`;
- **rvalue**, включая временные узлы и временные векторы, сохраняются по значению — копируются или перемещаются в узел.

`std::reference_wrapper` — небольшой копируемый объект, содержащий ссылку; сам операнд он не копирует и его время жизни не продлевает.

Шаблонный параметр `T&&` при выводе `T` используется как **forwarding reference**. `std::forward<T>` сохраняет категорию значения исходного аргумента. Поэтому `capture` может различить существующий объект и временный.

### Полная программа: векторы и узел суммы

```cpp
#include <cassert>
#include <cstddef>
#include <functional>
#include <initializer_list>
#include <iostream>
#include <stdexcept>
#include <type_traits>
#include <utility>
#include <vector>

struct ExprTag {};

template<class Derived>
struct Expr : ExprTag {
    const Derived& derived() const {
        return static_cast<const Derived&>(*this);
    }
};

template<class T>
inline constexpr bool is_expression_v =
    std::is_base_of_v<ExprTag, std::decay_t<T>>;

// Lvalue сохраняем по ссылке, rvalue — по значению.
template<class T>
using Closure = std::conditional_t<
    std::is_lvalue_reference_v<T>,
    std::reference_wrapper<const std::remove_reference_t<T>>,
    std::decay_t<T>
>;

template<class T>
Closure<T> capture(T&& value) {
    if constexpr (std::is_lvalue_reference_v<T>) {
        return std::cref(value);
    } else {
        return std::forward<T>(value);
    }
}

// Получаем исходный операнд из сохранённой ссылки или значения.
template<class T>
const T& read_operand(const std::reference_wrapper<const T>& value) {
    return value.get();
}

template<class T>
const T& read_operand(const T& value) {
    return value;
}

class Vec : public Expr<Vec> {
public:
    explicit Vec(std::size_t size) : data_(size) {}
    Vec(std::initializer_list<double> values) : data_(values) {}

    std::size_t size() const {
        return data_.size();
    }

    double operator[](std::size_t i) const {
        return data_[i];
    }

    double& operator[](std::size_t i) {
        return data_[i];
    }

private:
    std::vector<double> data_;
};

template<class Left, class Right>
class Sum : public Expr<Sum<Left, Right>> {
public:
    Sum(Left left, Right right)
        : left_(std::move(left)), right_(std::move(right)) {
        if (read_operand(left_).size() != read_operand(right_).size()) {
            throw std::invalid_argument("Different vector sizes");
        }
    }

    std::size_t size() const {
        return read_operand(left_).size();
    }

    double operator[](std::size_t i) const {
        return read_operand(left_)[i] + read_operand(right_)[i];
    }

private:
    Left left_;
    Right right_;
};

template<class L, class R,
         std::enable_if_t<is_expression_v<L> && is_expression_v<R>, int> = 0>
auto operator+(L&& left, R&& right) {
    return Sum<Closure<L>, Closure<R>>(
        capture(std::forward<L>(left)),
        capture(std::forward<R>(right))
    );
}

template<class E>
Vec evaluate(const Expr<E>& expression) {
    const E& expr = expression.derived();
    Vec result(expr.size());

    for (std::size_t i = 0; i < result.size(); ++i) {
        result[i] = expr[i];
    }

    return result;
}

int main() {
    Vec a{1.0, 2.0, 3.0};
    Vec b{10.0, 20.0, 30.0};
    Vec c{100.0, 200.0, 300.0};

    auto expression = a + b + c;
    Vec result = evaluate(expression);

    assert(result[0] == 111.0);
    assert(result[1] == 222.0);
    assert(result[2] == 333.0);

    // Временный Vec хранится внутри выражения по значению.
    auto with_temporary = a + Vec{4.0, 5.0, 6.0};
    Vec other = evaluate(with_temporary);
    assert(other[0] == 5.0);

    for (std::size_t i = 0; i < result.size(); ++i) {
        std::cout << result[i] << ' ';
    }
    std::cout << '\n';  // 111 222 333
}
```

### Разбор по шагам

**1. `ExprTag` отмечает выражения.** `is_expression_v<T>` проверяет, наследуется ли тип после `std::decay_t` от маркера. Это условие рассчитано на используемые здесь завершённые типы операндов.

`std::decay_t` снимает ссылки и верхнеуровневые `const`/`volatile`; для массивов и функций у него также есть преобразования к указателям. Здесь операнды — объекты классов.

**2. `Vec` хранит данные.** Его `operator[]` читает или изменяет готовый элемент, а `size()` сообщает длину.

**3. `Sum` хранит описание операции.** Его конструктор сохраняет операнды и проверяет размеры. Арифметического сложения элементов на этом этапе нет.

**4. `operator+` строит узел.** Для `a + b` оба аргумента — lvalue, поэтому внутри узла находятся обёртки ссылок на `a` и `b`.

**5. Во внешней сумме временный узел сохраняется по значению.** В `(a + b) + c` левый аргумент внешнего `operator+` — временный объект `Sum`. Он перемещается в новый узел. Ссылки внутри него продолжают обозначать `a` и `b`.

**6. `evaluate` материализует результат.** Создаётся один результирующий вектор, затем каждый элемент вычисляется через внешний узел. Вызов его `operator[]` обращается к внутренним операциям.

**7. SFINAE ограничивает оператор.** Аргумент шаблона с `enable_if_t` позволяет этой перегрузке участвовать только тогда, когда оба операнда помечены как выражения. Подробное объяснение механизма дано ниже.

### Условия корректного использования

- Все объекты, на которые сохранены ссылки, должны существовать до завершения вычисления.
- Пока выражение используется, нельзя менять размеры его ссылочных операндов: проверка совместимости выполнена при создании узлов. Присваивание вектору другого размера также нарушает это условие.
- Индекс должен находиться в пределах `[0, size())`; `operator[]` здесь не проверяет границы.
- Операнды читаются через константный интерфейс. Это не запрещает изменить исходный вектор через другую неконстантную ссылку между вычислениями.

Это модель поэлементного сложения с явной материализацией. Матричное умножение, представления подмассивов, автоматический выбор временных объектов и смешанные числовые типы требуют дополнительных решений.

## Ограничения и ошибки ленивых выражений

### auto может сохранить операцию, а не результат

```cpp
auto expression = a + b;
Vec snapshot = evaluate(expression);

a[0] = 1000.0;

Vec updated = evaluate(expression);
```

`snapshot` хранит уже вычисленные значения. `expression` хранит ссылки на `a` и `b`, поэтому `updated` учитывает изменение `a`.

Такое поведение необходимо понимать при использовании `auto`: вывод типа сохраняет фактический возвращаемый тип, которым может оказаться узел операции. Аналогичные особенности выражений рассматриваются в документации Eigen в разделе [Common pitfalls](https://eigen.tuxfamily.org/dox/TopicPitfalls.html).

### Висячие ссылки при возврате выражения

Следующая функция возвращает выражение, которое ссылается на локальные векторы:

```cpp
auto bad_expression() {
    Vec a{1.0, 2.0};
    Vec b{3.0, 4.0};
    return a + b;
}
```

После выхода из функции `a` и `b` уничтожены. Объект выражения возвращён по значению, но его ссылки не стали владельцами исходных векторов. Вычислять такой результат нельзя.

Корректный вариант — материализовать результат до уничтожения операндов:

```cpp
Vec good_result() {
    Vec a{1.0, 2.0};
    Vec b{3.0, 4.0};
    return evaluate(a + b);
}
```

Возможен и другой дизайн: явно передать владение операндами в выражение. Но владение только внешним узлом не устраняет висячие ссылки, уже находящиеся внутри него.

### Алиасинг: результат и исходные данные пересекаются

**Алиасинг** означает, что разные обозначения обращаются к одной и той же памяти или к пересекающимся областям памяти.

Для поэлементной суммы запись `a[i] = a[i] + b[i]` обычно безопасна: при вычислении позиции `i` не требуются старые значения других элементов `a`.

Для транспонирования, сдвига или матричного умножения ситуация иная. Наивный алгоритм `A = A * A`, записывающий результат прямо в `A`, может испортить исходные элементы, которые понадобятся для последующих вычислений.

Поэтому библиотеке иногда нужно сначала вычислить временный результат и только затем заменить исходный объект. **Устранение всех временных объектов не является безусловной целью.** Правильность вычисления имеет приоритет.

В приведённой реализации `evaluate` создаёт отдельный вектор. Поэтому выражение `a = evaluate(a + b)` сначала получает независимый результат и лишь затем выполняет присваивание.

### Повторное вычисление дорогих подвыражений

Если узел не кэширует результат, каждый запрос повторяет работу. Подвыражение, которое используется много раз, может оказаться выгоднее материализовать один раз.

Например, при вычислении произведений матриц значение одного элемента подвыражения может понадобиться многократно. Полная ленивость способна увеличить число операций по сравнению с предварительным вычислением промежуточной матрицы.

В практических библиотеках используются правила выбора стратегии вычисления. Eigen описывает сохранение временных результатов ради корректности и производительности в разделе [Lazy Evaluation and Aliasing](https://eigen.tuxfamily.org/dox/TopicLazyEvaluation.html).

### Цена сложности

Шаблоны выражений могут увеличивать время компиляции, размер сообщений об ошибках, число специализаций и сложность отладки. Выигрыш во время выполнения зависит от операций, объёма данных, оптимизаций компилятора и архитектуры процессора.

Для чисел с плавающей точкой нужно также учитывать порядок операций: изменение группировки сложений может изменить округление. В разобранном выражении поэлементная формула сохраняет группировку `(a[i] + b[i]) + c[i]`.

## SFINAE: принцип и границы применимости

### Определение

**SFINAE, Substitution Failure Is Not An Error** — правило, согласно которому определённые ошибки подстановки аргументов шаблона приводят к неудаче вывода и исключению соответствующего варианта, а не сразу к ошибке всей программы.

Для перегрузок функций практический смысл таков: если при формировании кандидата возникла допустимая для SFINAE ошибка, этот вариант не участвует дальше в выборе. Затем компилятор рассматривает оставшиеся варианты.

Но если подходящих кандидатов не осталось или между ними неоднозначность, вызов всё равно некорректен.

### Первая программа: наличие вложенного типа

```cpp
#include <cassert>

template<class T>
int classify(const T&, typename T::value_type* = nullptr) {
    return 1;
}

int classify(...) {
    return 0;
}

struct Container {
    using value_type = int;
};

int main() {
    assert(classify(Container{}) == 1);
    assert(classify(42) == 0);
}
```

Разберём вызов `classify(42)`:

1. По первому аргументу выводится `T = int`.
2. При формировании типа второго параметра требуется `typename int::value_type*`.
3. Такого типа нет; подстановка в данном контексте не удаётся.
4. Шаблонный вариант исключается.
5. Остаётся `classify(...)`, и вызывается он.

Для `Container` вложенный тип существует. Оба варианта доступны, но шаблонный даёт более подходящее соответствие аргументу, чем передача через многоточие.

Многоточие здесь используется только как учебный резервный вариант. Для прикладного интерфейса часто удобнее другая ограниченная перегрузка, признак типа или `requires`.

### Непосредственный контекст подстановки

**SFINAE не подавляет произвольные ошибки в шаблонах.** Важен **непосредственный контекст, immediate context**, где производится подстановка.

Типичные места для проверки: зависимые типы параметров и возвращаемого значения функции, а также объявления параметров шаблона. Ошибки в теле функции и ошибки отдельно инстанцируемых вспомогательных шаблонов обычно не относятся к этому контексту.

Сравним:

```cpp
// Проверяемое имя находится в типе функции.
template<class T>
auto first(const T&) -> typename T::value_type;

// Проверяемое имя находится в теле.
template<class T>
void second(const T&) {
    typename T::value_type element{};
    (void)element;
}
```

У `first<int>` формирование кандидата может завершиться неудачей подстановки. Если `second<int>` выбран и его тело требуется инстанцировать, отсутствие `int::value_type` — обычная ошибка компиляции; компилятор не возвращается к выбору другой перегрузки.

Нормативные границы правила приведены в разделе стандарта [temp.deduct.general](https://timsong-cpp.github.io/cppwp/n4950/temp.deduct.general).

### Ошибка во вспомогательном шаблоне

```cpp
template<class T>
struct Extract {
    using type = typename T::missing;
};

template<class T>
void inspect(T, typename Extract<T>::type* = nullptr);

void inspect(...);

// inspect(0);  // Ошибка при инстанцировании Extract<int>.
```

Хотя `Extract<T>::type` записан в типе параметра, для его получения приходится инстанцировать определение `Extract<int>`. Ошибка внутри этого определения не превращается автоматически в мягкую неудачу подстановки.

Отсюда правило: проверку по возможности формулируют прямо в SFINAE-контексте либо используют вспомогательные traits, которые специально спроектированы так, чтобы отсутствие нужного свойства выражалось отсутствием специализации или значением `false`.

### Ошибки, не зависящие от T

SFINAE связано с подстановкой конкретных аргументов. Независимая от параметров ошибка, например заведомо неизвестное независимое имя, не становится допустимой только потому, что записана в шаблоне.

Аналогично, `std::enable_if_t<false, int>` в обычном нешаблонном объявлении просто некорректен: контекста отбора шаблонного кандидата там нет.

## Управление перегрузками через enable_if

### Устройство std::enable_if

`std::enable_if` из `<type_traits>` условно предоставляет вложенный тип:

```cpp
template<bool Condition, class T = void>
struct my_enable_if {};

template<class T>
struct my_enable_if<true, T> {
    using type = T;
};
```

При `Condition == true` существует `type`, равный `T`. При `false` такого имени нет. Если обращение к нему находится в подходящем контексте подстановки, кандидат исключается.

Сокращение C++14:

```cpp
std::enable_if_t<Condition, T>
```

означает

```cpp
typename std::enable_if<Condition, T>::type
```

Такое устройство задано в разделе стандартной библиотеки [meta.trans.other](https://eel.is/c++draft/meta.trans.other).

### Ограничение через возвращаемый тип

```cpp
#include <cassert>
#include <type_traits>

template<class T>
std::enable_if_t<std::is_integral_v<T>, T>
twice_integral(T value) {
    return value + value;
}

int main() {
    assert(twice_integral(7) == 14);
    // twice_integral(2.5);  // Подходящего кандидата нет.
}
```

Для `T = int` возвращаемый тип — `int`. Для `T = double` требуется отсутствующий `std::enable_if<false, double>::type`, поэтому кандидат исключается.

Этот пример не решает задачу проверки арифметического переполнения. Для знаковых целых нужно выбирать значения, результат сложения которых представим в соответствующем типе.

Возвращаемый тип обычно не используется для вывода `T` по ожидаемому типу результата. Здесь `T` выводится по аргументу функции.

### Ограничение через нетиповой параметр шаблона

```cpp
template<class T,
         std::enable_if_t<std::is_integral_v<T>, int> = 0>
T twice_integral(T value) {
    return value + value;
}
```

Если условие выполнено, второй параметр шаблона — целочисленный параметр типа `int` со значением по умолчанию `0`. Если условие не выполнено, нельзя сформировать тип этого параметра, и вариант исключается.

Такая запись оставляет возвращаемый тип свободным и подходит в том числе для ограничения конструкторов, у которых нет возвращаемого типа.

### Две взаимоисключающие перегрузки

```cpp
#include <cassert>
#include <type_traits>

template<class T,
         std::enable_if_t<std::is_integral_v<T>, int> = 0>
const char* category(T) {
    return "integral";
}

template<class T,
         std::enable_if_t<std::is_floating_point_v<T>, int> = 0>
const char* category(T) {
    return "floating";
}

int main() {
    assert(category(3)[0] == 'i');
    assert(category(3.5)[0] == 'f');
}
```

`std::is_integral` включает также `bool` и символьные целочисленные типы. Если интерфейс должен их исключить, это нужно выразить отдельным условием.

SFINAE не задаёт порядок предпочтения между произвольными логическими условиями. Если обе перегрузки остаются допустимыми и обычные правила перегрузки не выбирают лучшую, возникнет неоднозначность.

### Ошибка: различать шаблоны только аргументом по умолчанию

```cpp
// Некорректно: второе объявление не создаёт нужную новую перегрузку.
template<class T, class = std::enable_if_t<std::is_integral_v<T>>>
void process(T) {}

template<class T, class = std::enable_if_t<std::is_floating_point_v<T>>>
void process(T) {}
```

Аргументы шаблона по умолчанию не используются для такого различения объявлений. В результате возникают конфликтующие определения одного шаблона.

Один из вариантов исправления — применить показанную выше форму с зависимым **типом нетипового параметра**:

```cpp
template<class T,
         std::enable_if_t<std::is_integral_v<T>, int> = 0>
void process(T) {}

template<class T,
         std::enable_if_t<std::is_floating_point_v<T>, int> = 0>
void process(T) {}
```

### Ошибка: зависимость только от параметра класса

```cpp
template<class T>
struct BadBox {
    std::enable_if_t<std::is_integral_v<T>, void> run() {}
};

// BadBox<double> box;  // Объявление run уже нельзя сформировать.
```

Здесь `run` — обычный метод специализации класса. Формирование `BadBox<double>` требует получить его объявление, и неудача не является отбором перегрузки шаблонного метода.

Если нужен именно условный метод в C++17, его можно сделать шаблонным и отложить проверку до подстановки собственного параметра:

```cpp
template<class T>
struct Box {
    template<class U = T,
             std::enable_if_t<std::is_same_v<U, T> &&
                              std::is_integral_v<U>, int> = 0>
    void run() {}
};
```

Проверка `std::is_same_v<U, T>` не позволяет включить метод для `Box<double>` явным указанием постороннего целочисленного `U`. В C++20 условный метод проще выразить через `requires`.

## Обнаружение операций через decltype и void_t

### decltype и невыполняемый контекст

`decltype(expression)` получает тип выражения. Сам операнд `decltype` не вычисляется, но должен быть корректным по правилам языка.

```cpp
decltype(1 + 2.0) value = 0.0;  // Тип double.
```

Точный результат `decltype` зависит и от категории значения: для произвольного выражения типа `T` lvalue даёт `T&`, xvalue — `T&&`, prvalue — `T`. Для непомещённых в скобки имён и обращений к членам действует специальное правило получения объявленного типа.

В проверках операций нас часто интересует не конкретный полученный тип, а сам факт, что выражение допустимо.

### std::declval

`std::declval<T>()` из `<utility>` позволяет описать выражение с объектом типа `T`, не создавая его. Использовать `declval` можно только в невыполняемом контексте.

```cpp
decltype(std::declval<const T&>().size())
```

означает: «тип результата вызова `size()` у константного lvalue типа `T`». Проверка не требует конструктора по умолчанию.

Категория и константность важны:

- `std::declval<T&>()` моделирует изменяемый lvalue;
- `std::declval<const T&>()` — константный lvalue;
- `std::declval<T>()` для обычного нессылочного `T` — rvalue-ссылку, то есть выражение категории xvalue.

Существование `size()` у изменяемого объекта не гарантирует возможность вызвать его у константного объекта.

### Expression SFINAE: проверка выражения в возвращаемом типе

```cpp
#include <cassert>
#include <cstddef>
#include <vector>

template<class T>
auto measured_size(const T& object) -> decltype(object.size()) {
    return object.size();
}

std::size_t measured_size(...) {
    return 0;
}

int main() {
    std::vector<int> values{10, 20, 30};
    assert(measured_size(values) == 3);
    assert(measured_size(42) == 0);
}
```

Выражение `object.size()` проверяется в зависимом возвращаемом типе. Если оно некорректно, шаблонная перегрузка исключается.

Запись только с автоматическим выводом возвращаемого типа не равнозначна этой проверке:

```cpp
template<class T>
auto unsafe_size(const T& object) {
    return object.size();
}
```

Чтобы вывести тип результата, понадобится инстанцировать тело. Ошибка в нём не превращается в SFINAE только из-за ключевого слова `auto`.

### std::void_t и частичная специализация

`std::void_t<Types...>` из `<type_traits>`, доступный с C++17, обозначает `void`, если удалось корректно сформировать все переданные типы.

Он удобен для техники **detection idiom** — построения признаков, проверяющих наличие типов или допустимость выражений.

```cpp
#include <cassert>
#include <type_traits>
#include <utility>
#include <vector>

template<class T, class = void>
struct has_const_size : std::false_type {};

template<class T>
struct has_const_size<T, std::void_t<
    decltype(std::declval<const T&>().size())
>> : std::true_type {};

struct MutableOnly {
    int size() { return 1; }
};

int main() {
    static_assert(has_const_size<std::vector<int>>::value);
    static_assert(!has_const_size<int>::value);
    static_assert(!has_const_size<MutableOnly>::value);
}
```

Механизм для `has_const_size<std::vector<int>>`:

1. Второй аргумент по умолчанию равен `void`.
2. При проверке частичной специализации вызов `size()` у константного вектора корректен.
3. `decltype(...)` даёт тип результата; `void_t` преобразует его в `void`.
4. Частичная специализация подходит и наследует `std::true_type`.

Для `int` выражение некорректно, поэтому эта специализация не подходит. Используется первичный шаблон с `std::false_type`.

**Проверяется именно допустимость выражения.** Этот признак не утверждает, что результат является количеством элементов, что он неотрицателен или что операция имеет определённую сложность.

### Проверка типа результата операции

Если требуется не только наличие `size()`, но и возможность преобразовать его результат к `std::size_t`, условие можно уточнить:

```cpp
#include <cstddef>
#include <type_traits>
#include <utility>

template<class T, class = void>
struct has_size_result : std::false_type {};

template<class T>
struct has_size_result<T, std::void_t<
    decltype(std::declval<const T&>().size())
>> : std::bool_constant<std::is_convertible_v<
    decltype(std::declval<const T&>().size()),
    std::size_t
>> {};
```

Дополнительная проверка всё ещё описывает только свойство типа. Например, отрицательный `int` допускает неявное преобразование к `std::size_t`, но может не иметь подходящего смысла для размера. Семантические требования нужно формулировать отдельно.

## Сопоставление техник и современные альтернативы

### Какие задачи решаются

| Техника | Основной вопрос | Типичный результат |
|---|---|---|
| CRTP | Как общей базе вызвать реализацию конкретного наследника? | Статический интерфейс и повторное использование кода |
| Шаблоны выражений | Как представить составную операцию до вычисления результата? | Типизированные узлы и управляемая материализация |
| SFINAE | Какие шаблонные варианты допустимы для данных типов? | Исключение неподходящих кандидатов или специализаций |
| `if constexpr` | Какую ветку выбранной реализации инстанцировать? | Один шаблон с разными ветками |
| Concepts и `requires` | Как явно записать ограничения интерфейса? | Ограниченные шаблоны и проверяемые требования |

В векторном примере эти задачи разделены:

1. CRTP предоставляет доступ к конкретному выражению через `Expr<Derived>`.
2. `Sum` описывает сложение и вычисляет элемент по требованию.
3. SFINAE ограничивает перегруженный `operator+` выражениями.
4. `if constexpr` выбирает способ хранения операнда внутри `capture`.

### if constexpr: выбор внутри реализации

`if constexpr` появился в C++17. В шаблонном контексте после определения условия ненужная ветка не инстанцируется. Это позволяет поместить разные операции в одно тело:

```cpp
#include <type_traits>

template<class T>
auto absolute_value(T value) {
    if constexpr (std::is_unsigned_v<T>) {
        return value;
    } else {
        return value < 0 ? -value : value;
    }
}
```

Здесь подразумеваются подходящие арифметические типы и значения, для которых отрицание представимо. В частности, отрицание минимального знакового целого требует отдельной обработки.

**Отличие от SFINAE:** `if constexpr` выбирает ветку в уже выбранном шаблоне; сам по себе он не исключает функцию из набора перегрузок. Вызов с неподходящим типом может закончиться ошибкой при инстанцировании тела.

Отброшенная ветка всё равно должна быть синтаксически корректной. В частности, `if constexpr` не предназначен для сокрытия произвольного некорректного кода, не зависящего от параметров.

### Concepts и requires в C++20

Для новых интерфейсов в C++20 ограничения часто удобнее записывать явно:

```cpp
#include <cassert>
#include <concepts>
#include <cstddef>
#include <vector>

template<std::integral T>
T twice_integral(T value) {
    return value + value;
}

template<class T>
concept ConstSized = requires(const T& object) {
    { object.size() } -> std::convertible_to<std::size_t>;
};

template<ConstSized T>
std::size_t measured_size(const T& object) {
    return object.size();
}

template<class T>
struct Box {
    void run() requires std::integral<T> {}
};

int main() {
    assert(twice_integral(7) == 14);
    assert(measured_size(std::vector<int>{1, 2, 3}) == 3);
    Box<int>{}.run();
    Box<double> box;  // Класс корректен, но run() недоступен по ограничению.
    (void)box;
}
```

`requires`-выражение проверяет перечисленные требования в шаблонном контексте. Невыполненные требования не делают ограниченный интерфейс подходящим для данного типа.

Concepts выражают ограничения напрямую и обычно дают более понятную диагностику, чем глубоко вложенные `enable_if`. Однако они не исправляют произвольные ошибки в телах функций или во вспомогательных инстанцированиях. Семантическое содержание вроде «размер неотрицателен» также не доказывается одной проверкой выражения.

Отношение предпочтения ограниченных перегрузок определяется правилами constraints и subsumption; компилятор не доказывает произвольные логические следствия между написанными условиями.

### Как выбрать подход

- Нужна единая базовая реализация, вызывающая операции конкретного класса: рассмотрите CRTP.
- Нужны ленивые составные операции и контроль промежуточных массивов: рассмотрите шаблоны выражений.
- Нужен отбор перегрузок в C++11–17: используйте SFINAE и traits.
- Нужен выбор реализации внутри одного шаблона C++17: используйте `if constexpr`.
- Нужны явные ограничения в C++20: используйте concepts и `requires`, если они подходят к интерфейсу.
- Нужна только обобщённая функция, вызывающая доступный метод: обычного шаблона может быть достаточно; CRTP не обязателен.

## Вопросы и задачи для самопроверки

### Вопросы с краткими ответами

**1. Выполняется ли метод CRTP обязательно при компиляции?** Нет. При компиляции определяется реализация; сама обработка данных может происходить при выполнении.

**2. Почему у разных наследников CRTP нет одной общей специализации базы?** Они передают разные типы: например, `Shape<Circle>` отличается от `Shape<Rectangle>`.

**3. Что хранит `auto expression = a + b` в ленивой библиотеке?** Обычно узел операции. Готовые значения появляются после материализации.

**4. Достаточно ли сохранить внешний узел по значению, чтобы избежать всех висячих ссылок?** Нет. Его внутренние узлы могут ссылаться на уже уничтоженные объекты.

**5. Убирает ли SFINAE ошибку в теле выбранной функции?** Нет. Такая ошибка обычно приводит к отказу компиляции.

**6. Что происходит, если SFINAE исключило все подходящие перегрузки?** Вызов некорректен: подходящей функции нет.

**7. Зачем нужен `declval`, если можно написать `T{}`?** `declval` не требует создания объекта и позволяет явно выбрать ссылку и константность для проверки.

**8. Гарантирует ли ленивое вычисление отсутствие временных объектов и максимальную скорость?** Нет. Временные результаты иногда необходимы для правильности и полезны для производительности.

### Задача 1. Общая операция через CRTP

Добавьте в `Repeatable<Derived>` метод `repeat_twice()`, который вызывает `step()` ровно два раза. Проверьте его с двумя наследниками: один увеличивает число, другой добавляет символ в строку.

**Ориентир:** общая база не должна знать тип хранимых данных наследника; ей нужна только операция `step()`.

### Задача 2. Время жизни выражения

Объясните, какие из записей безопасны для реализации выше:

```cpp
auto first = a + b + c;
auto second = a + Vec{4.0, 5.0, 6.0};
auto third = bad_expression();
```

**Ответ:** первые две безопасны при выполнении условий времени жизни и размеров. Третье выражение содержит ссылки на уничтоженные локальные векторы; его дальнейшее вычисление недопустимо.

### Задача 3. Признак наличия операции сложения

Реализуйте `has_plus<T>` через `std::void_t`, проверяющий допустимость

```cpp
std::declval<const T&>() + std::declval<const T&>()
```

**Ориентир:** первичный шаблон наследуется от `std::false_type`, частичная специализация с `void_t<decltype(...)>` — от `std::true_type`. Признак проверяет наличие операции, но не обязан требовать результата типа `T`.

### Задача 4. Где сработает SFINAE

Сравните две декларации и определения:

```cpp
template<class T>
auto f(T object) -> decltype(object.begin());

template<class T>
auto g(T object) {
    return object.begin();
}
```

**Ответ:** у `f` проверка находится в зависимом возвращаемом типе и может исключить кандидата. У `g` вывод типа требует инстанцирования тела; ошибка там не является мягким исключением перегрузки.

## Главное

1. **CRTP передаёт тип наследника в шаблон базы.** База получает доступ к конкретной реализации через корректное приведение к `Derived`.
2. **Статический выбор реализации не равен вычислению результата при компиляции.** Методы CRTP и поэлементные операции могут выполняться над обычными данными времени выполнения.
3. **Шаблоны выражений представляют вычисление узлами.** Это позволяет отложить материализацию и объединить поэлементные операции в один проход.
4. **Время жизни операндов — часть корректности ленивого интерфейса.** Владение временными узлами не продлевает время жизни объектов, на которые они ссылаются.
5. **Промежуточные результаты иногда необходимы.** Они предотвращают ошибки алиасинга и могут избавлять от повторного вычисления дорогих операций.
6. **SFINAE исключает вариант при допустимой ошибке подстановки.** Ошибки тела выбранной функции и отдельно инстанцируемых конструкций не скрываются этим правилом.
7. **`enable_if`, `decltype`, `declval` и `void_t` позволяют описывать проверки типов и операций.** Проверка корректности выражения не доказывает его прикладной смысл.
8. **`if constexpr` выбирает ветку, а constraints C++20 ограничивают интерфейс.** Выбор средства зависит от того, нужно ли менять тело реализации или состав допустимых перегрузок.
